# Plan review: harden exiting-child test

## Verdict: APPROVED WITH CHANGES

1. **The diagnosis of the observed `agent_busy` failure is correct.** The test record has `pid: 123` and no `create_token`. During `_prepare`, `_agent_alive()` calls `process_manager.health_check("123", expected_token=None)`. With no matching in-memory process entry, `_pid_health_with_token()` falls back to `_pid_alive()`. If PID 123 is live and probeable (or, on Windows, `OpenProcess` fails specifically with access denied), it is classified alive. Because the fixture has no waiting marker, `_prepare` returns `wait_reason="agent_busy"`; the injected clock then exhausts the call budget and the public result reports that reason. Conversely, Linux's `_pid_alive()` currently maps every `OSError`, including `EPERM`, to false, explaining why the same sentinel can look dead on one host and alive on another. This is a fixture leak, not evidence of a production state-machine defect.

2. **Pin both liveness decisions, but simplify the proposed ownership setup.** Capturing the spawned process's creation token before `wait()` and asserting that it is non-`None` is deterministic on the supported Linux and Windows CI platforms: Linux retains `/proc/<pid>/stat` while the unreaped child is a zombie, and Windows' `Popen` retains a process handle until the test has had an opportunity to query its creation time. The wrapper must save the original bound `health_check` before monkeypatching it, or delegation will recurse. It should also reject unexpected handles rather than silently inventing answers. A cleaner variant than special-casing the unrelated string `"123"` is to rewrite this test's agent record before taking `before` so its `pid` and `create_token` are the exited fixture's `(pid, token)`, then use a narrow wrapper that supplies that token when confirmation calls `health_check` without one. The normal `_agent_alive()` call is then already token-pinned, and the same real exited process drives both decisions. An equally valid, slightly more mocked alternative is to return the `Popen` and have the narrow wrapper derive liveness from `proc.poll()`.

3. **The proposed wrapper does not destroy A3's intent if it remains narrow, but the plan overstates what stays “real.”** The directly spawned fixture process is not in `process_manager._processes`, so delegated `health_check` does not exercise the manager's tracked `Popen.poll()` branch; it exercises the token-aware OS-PID fallback. The meaningful A3 property is still retained: an actual child is created and actually terminates, the scanner finds no receipt, `confirm_delivery()` observes it dead at elapsed time zero, returns `resume_not_confirmed`, and finalization leaves the record unchanged. The test should continue asserting that resume was attempted and the record/pending marker were unchanged. The plan should replace its “real poll/exit transition” wording with “real process termination observed through token-aware liveness.” Token parsing and PID-reuse behavior are already directly covered in `tests/test_pid_reuse.py` and need not be re-proved through a broad stub here.

4. **The post-resume PID-reuse discussion needs qualification; it is not a demonstrated production bug in the reviewed path.** The fake backend returns an arbitrary, unregistered PID, so its confirmation callback reaches bare-PID fallback unless the test wrapper supplies a token. Built-in process backends resume through `process_manager.spawn_process()`, which records the returned process/pane in the manager. Their immediate confirmation checks hit tracked process or pane state before `_pid_health_with_token()`, so a host PID being recycled after an immediate exit does not turn that tracked child into a live foreign process. The plan's statement that the second race is generally “reachable on the same busy host” omits this distinction. It is reachable in this test double (and potentially in a future backend that violates the built-in ownership pattern), not shown for current built-in production resumes.

5. **No production change is warranted for this flake.** Passing a newly captured token into confirmation could be reasonable defense-in-depth for untracked third-party backends, but it is a separate behavior change and would need a production-level regression test plus a decision about token acquisition failure and non-PID handles. It should not be smuggled into this test-hardening task. The focused test-only fix is sufficient once both fixture probes are explicitly pinned. Revise the plan to avoid presenting the fake backend's unregistered-handle behavior as proof that production confirmation is currently PID-reuse-unsafe.

6. **Acceptance criteria should include the exact regression simulation.** Besides repeated runs on Linux and Windows, add a focused test/run in which the original record's numeric PID is intentionally a known-live PID without a token and demonstrate that the unmodified fixture can take the `agent_busy` path; then verify the hardened test no longer consults that ambient PID. For the final implementation, assert a non-`None` token before reaping, capture the original `health_check` before monkeypatching, and fail on any unexpected handle. These checks make the test deterministic without converting confirmation itself into a predetermined mocked outcome.
