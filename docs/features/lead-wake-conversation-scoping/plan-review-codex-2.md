# Plan review: lead-wake conversation scoping v2

## Verdict

**APPROVED WITH CHANGES**

The install-time PID plus creation-token binding is a sound replacement for the v1 disk claim. Findings 1-3 from the first review dissolve as ownership defects: the hook no longer writes ownership, passive MCP reads cannot steal the baked owner, and there is only one ownership-establishing operation (`install_lead_wake`, excluding removal). They do, however, leave one relevant lesson behind: hook-side session discovery is still impure, so v2 should perform the now-session-independent ownership gate before discovery rather than after it.

Finding 4 is substantively addressed by the PID/token pair. Finding 9's preferred install-time option is adopted, but its minimum active-session gate and migration default are not. Findings 5-10 are therefore only partly addressed, for the reasons below. The changes are local to the proposed design and tests; they do not require returning to a disk claim.

## Findings

1. **MAJOR — D1b is one row too late under the new design; placing it after D1 preserves bystander session side effects.** `lead_wake._resolve_session_dir` calls `server_simple._active_session_id(create=False)`. That path can scan bindings and agent registries, and single-candidate auto-adoption calls `_persist_session_binding`, which writes and prunes binding files. Therefore the plan's claim that D1b is “before any registry read” is false, and a non-owner can still cause session reads and binding mutation before being allowed. This is not a resurrection of v1's ownership theft—the baked argv remains immutable—but it is the same impure-discovery hazard that findings 1 and 3 exposed. The owner comparison needs no session directory, so the correct order is D0, validate/evaluate ownership, then identity/session resolution (D1), then D2. **Recommendation:** move D1b before `_resolve_session_dir`; require a foreign-owner test that patches `_resolve_session_dir` (or `_active_session_id`) to raise and proves it is never called, in addition to proving no registry, inbox, guard, or stdout activity.

2. **MAJOR — Missing baked ownership must fail silent; “keep today's behavior” leaves every legacy shared install with the original bug.** The hook cannot infer whether missing owner arguments mean a private per-agent settings file or a legacy shared settings file. Defaulting both to today's behavior makes upgraded-but-not-reinstalled project/user hooks continue nagging bystanders indefinitely, contradicting the stated goal. A log hint is not containment. **Recommendation:** make absence or partial presence of owner arguments allow with `D1b/owner-unknown`. Change `write_claude_settings` to emit an explicit private-mode argument (for example `--owner-mode private`) whose only meaning is “this settings file is already conversation-scoped; proceed without a PID gate.” Shared installation must emit `--owner-mode bound` plus both values. Reject inconsistent combinations. Keep `WIN_AGENT_TEAMS_LEAD_WAKE_OWNER=0` only as an explicit diagnostic opt-out that restores current behavior. Add migration tests for legacy shared, explicit private, complete bound, and every incomplete/malformed combination.

3. **MAJOR — Install-time host resolution remains the central unproven premise, so finding 5 is not fully dispositioned.** The Windows spike proves that a hook-launched process can reach a conversation-specific `claude.exe`, but it does not show that the top-level conversation's MCP server and its Stop hook independently select the same nearest host, nor that two simultaneous conversations select different hosts. It also does not prove the Linux image name or ancestry. If the server reaches only the shared outer Electron `claude.exe` while the hook selects the inner conversation process, the owner conversation is silent immediately; if either side selects a shared host, bystanders can match. Synthetic maps cannot settle that production topology. **Recommendation:** before treating the implementation as complete, capture paired server-side and hook-side chains for two top-level Claude CLI/Desktop conversations and a server-spawned Claude agent on Windows and Linux. State the exact supported basenames and verify them from those captures. Turn the captured shapes into separate server-chain/hook-chain fixtures that must resolve the same nearest PID for A and a different PID for B. The manual A/B smoke remains useful, but the evidence should be recorded and the Windows and Linux owner paths must be release gates, not merely planned future observation.

4. **MAJOR — The refusal policy is correct, but its contract and race-free “unchanged settings” guarantee need to be made implementable.** Refusing when no supported host or no creation token is safer than installing an unscoped shared hook. However, the proposed `procinfo` API returns only a nearest-host tuple or `None`, while the refusal promises to return the resolved chain; the plan does not identify an API that supplies that diagnostic. It also does not require owner resolution and token capture to finish before any path creation/read-modify-write work. **Recommendation:** define one diagnostic resolver result containing the bounded chain plus the selected host, validate the selected PID, obtain its token, and only then touch the target settings path. On every resolver/token failure return a stable reason (`host_not_found`, `host_token_unavailable`, or `host_walk_failed`) and the sanitized chain, with byte-identical settings and no newly created directory. Test host exit between the walk and token read, access-denied token reads, resolver exceptions, and an absent settings directory as well as an existing file.

5. **MAJOR — Claude Code's merge behavior supports the design, but test 22 does not prove the actual two-group configuration.** Current official Claude Code settings documentation states that JSON supplied through `--settings` merges with file-based settings and that array-valued settings concatenate across scopes. Thus a spawned agent can receive its private `Stop` group and a project/user shared `Stop` group, and v2's intended result—foreign shared group allows, private group acts—is plausible. It also means user, project, local, and `--settings` sources can contribute more than two groups; changing one settings file does not remove a lead-wake group from another scope. **Recommendation:** cite this dependency in the plan and add a production-shaped configuration test (or pinned Claude CLI smoke using `/hooks`/debug output) that loads user plus project plus explicit `--settings` sources. Assert that all expected groups are active, a foreign bound group is silent, the explicit-private group retains D2-D6 behavior, two lead-wake groups from different shared scopes do not get mistaken for one, and removal from one scope leaves the other scope intact. See the official [Claude Code settings precedence documentation](https://code.claude.com/docs/en/settings#settings-precedence).

6. **MAJOR — Finding 10 is not resolved until the owner generation is kept out of the shared member guard contract.** The plan says the guard schema gains owner PID/token while also promising no `member_wake` behavior change. `member_wake` imports and calls `lead_wake._apply_guard`; merely running M0-M5 tests does not specify whether existing member guard files are reinterpreted, reset, or rewritten with meaningless lead-owner fields. **Recommendation:** either split a lead-only owner-aware wrapper from the shared counter machinery, or pass an explicit optional guard generation used only by lead wake. Preserve the member guard filename and schema exactly. Add compatibility tests that seed an existing member progress file, drive repeated M3 and M5 decisions across the change, and assert the same counts, D6 timing, and serialized schema rather than only the same decision labels.

7. **MAJOR — Finding 7's entrypoint failure boundary is still underspecified.** The plan says argument parsing is inside the ownership fail-open boundary, but later describes an outer guard only around `evaluate` plus logging. `_parse_args` currently runs before `evaluate`, `argparse` can raise `SystemExit`, and stderr/stdout writes can raise after a valid decision. An `except Exception` does not catch `SystemExit`. “Never exits non-zero” therefore needs an explicit entrypoint structure, not only an evaluation guard. **Recommendation:** cover parse, evaluation, log rendering/writing, and decision writing so malformed/unknown argv, `SystemExit`, resolver/token exceptions, and broken stderr/stdout cannot escape as a nonzero hook. Do not let a failed fallback log attempt raise again. Add subprocess-level tests for unknown arguments, missing argument values, evaluation failure, stderr failure, and stdout failure; assert exit 0 and no block JSON whenever ownership cannot be proven.

8. **MAJOR — The restart-silence trade-off is safe for bystanders but not yet operationally recoverable.** A resumed/restarted owner correctly fails silent because its new process token must not inherit the old authority. That is an acceptable safety direction. The proposed mitigations are weak, however: a stderr line is not necessarily visible to the model or user, and a tool docstring is not proactively shown after restart, precisely when the hook no longer blocks and nothing prompts a reinstall. **Recommendation:** make `install_lead_wake` return an explicit binding-lifetime warning and document it in the reference page as a behavioral limitation, not just in the tool docstring. Add a deterministic sequence test: owner A blocks, A exits/restarts as A2 and the old command allows without disk reads, reinstall from A2 replaces the command, then A2 blocks and A remains silent. The implementation report's manual resume smoke should verify that the mismatch is actually diagnosable in Claude Code. If no proactive but bystander-safe recovery signal exists, retain restart silence and state plainly that wake enforcement does not survive a conversation restart.

9. **MAJOR — Finding 9's minimum active-session gate was dropped without justification.** Current `install_lead_wake` falls back to baking `_SESSION_BASE` when `_active_session_id(create=False)` returns empty. V2 changes owner binding but does not say whether this behavior remains. An install with no active session can later let hook-side auto-adoption choose an old cwd/identity candidate for the otherwise-correct owner, and the baked fallback is not itself a session directory. **Recommendation:** for `remove=False`, require both a resolved owner and a concrete active session directory, returning an unchanged-settings refusal otherwise; keep `remove=True` independent of both. If pre-session installation is a required UX, specify it explicitly and add a test proving the first later team creation is selected without old-session auto-adoption. Do not silently retain `_SESSION_BASE` as if it were a session-scoped value.

10. **MINOR — Installation is now an ownership handoff, but the shared-file update contract does not say so or make concurrent handoff safe.** Reinstalling the same scope deliberately removes A's command and writes B's, immediately silencing A and arming B. Concurrent read-modify-write calls can also lose unrelated settings or leave invalid JSON because the current implementation writes the settings file directly. Owner binding makes cross-conversation reinstall more likely and makes last-writer semantics observable. **Recommendation:** document per-settings-file last-successful-install-wins semantics, write through an atomic temporary replacement while preserving unrelated groups, and serialize concurrent installs if a suitable settings-file lock exists. Test A install, B reinstall, A/B evaluation after handoff, and a failed replacement leaving the original bytes valid and intact.

11. **MINOR — The remaining test plan should assert the seams, not only duplicate unit-level owner comparisons.** Cases 8, 9, and 21 substantially overlap and still miss the decisive boundaries. **Recommendation:** in addition to the tests named above, add: (a) command rendering and shell round-trip tests for PID/token arguments on Windows and POSIX; (b) an owner-row test proving session resolution is not called for mismatch, unknown owner, or malformed argv; (c) a matching-owner test proving D1 is still reached and existing D1-D6 behavior is unchanged; (d) host-name false-positive tests (`claude-helper`, outer Electron host, `codex`, and unknown wrappers must not match the Claude-only set); (e) process disappearance and PID/token mismatch on both install and hook sides; (f) exact guard migration tests for old lead files and unchanged member files; (g) real settings-scope merge evidence; and (h) subprocess exit-code/stdout assertions for every fail-open route. Report the Windows and Linux suites separately; a synthetic walk suite is not Linux verification.
