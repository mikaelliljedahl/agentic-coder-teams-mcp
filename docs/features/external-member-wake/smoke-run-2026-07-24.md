# External-member wake — live smoke run (2026-07-24)

Run before merging PR #38, from a real Claude Desktop deployment. Lead session
`800410a2-ef74-46d7-836b-2a1eb82caca9` (identity `team-lead`), external member
`visual-qa` in a separately-started interactive session on the same host/home.

## Result: PASS (feature works end-to-end) + 1 topology-dependent finding

### What was exercised

1. `create_join_ticket(name="visual-qa")` → member joined with
   `join_team(session_id, token)` and saved its `member_token`.
2. **`install_member_wake(joined_session_id, member_name="visual-qa")`** →
   `action:"installed"`, `scope:"user"` (the feature under test).
3. Member armed the reader-scoped watcher
   (`watch <joined dir> --reader visual-qa --timeout 3600`) as a background task
   and announced readiness upstream via `external_send`.
4. **Downstream (lead → external):** lead `send_message` to `visual-qa` with a
   distinctive marker (`DOWNSTREAM-PROBE-7Q4X-9F2K`) → `delivery:"inbox"`
   (pull-only, as designed). The member's **armed watcher fired with
   `reason:"message"` and re-invoked the member hands-free — zero manual
   polling** — which drained it via `external_read` and echoed the marker
   verbatim via `external_send`.
5. **Upstream (external → lead):** the lead's own watcher fired (exit 0) on the
   member's reply; `read_messages` drained the verbatim echo.
6. Lead sent the completion signal; member `read` it (`unread → 0`) and called
   `leave_team` → membership `left`. Both wake loops then self-cleared.

Both directions confirmed. Downstream hands-free pickup — the whole point of the
feature — worked exactly as designed.

### Finding: user-scope hook false-positives in a co-located lead session

Because the member installed member-wake at `scope="user"`
(`~/.claude/settings.json`) and the lead and member ran under the **same OS user
/ home on one machine**, the member-wake `Stop` hook also fired **in the lead's
own session**, nudging it to arm a `--reader visual-qa` watcher it should never
run. Root cause: the hook's M2 gate only checks whether `visual-qa` is a **live
membership** (true — the lead owns it), and it **cannot** tell "am I the member
session?" because the member keeps `IDENTITY = team-lead` by design and, on a
shared home/cwd, the disk-based session discovery does not cleanly separate the
two sessions. This is the exact Option A single-home foot-gun the design flagged.

- **Severity:** cosmetic. The nag is a harmless block (never-unstoppable
  contract holds, no-progress guard bounds it), and it self-clears the moment the
  member is `left`/`killed` (M2 fail-open).
- **Not present in the supported deployment:** a member running in a separate
  Desktop profile via `WIN_AGENT_TEAMS_EXTERNAL_ONLY=1`, or on a separate
  machine, has its own home/settings and never loads the lead's hook — no false
  positive.
- **Real fix:** Option B (self-locating member-wake via a membership-pointer file
  in the member session's own dir) is the documented follow-up; combined with
  separate profiles it removes the ambiguity entirely.
- **Recommended pre-merge mitigation:** strengthen the `install_member_wake`
  docstring to warn that on a shared home the hook also fires in a co-located
  lead session (harmless, self-clears on leave), and to prefer the separate
  `WIN_AGENT_TEAMS_EXTERNAL_ONLY` profile for a real member.
