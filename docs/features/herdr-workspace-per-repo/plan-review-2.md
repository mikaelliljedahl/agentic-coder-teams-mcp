1. **BLOCKER — Closing a workspace merely because this spawn created it is unsafe once the creation lock has been released.** The revised plan releases the per-label lock when `_create_tab` returns (`docs/features/herdr-workspace-per-repo/plan.md:107-121`), before `spawn_process` runs the command, reads the PID/token, writes provenance, and commits the record (`src/claude_teams/backends/process_manager.py:2716-2755`). During that interval a second spawn can list and reuse the new workspace. If the first spawn then fails, the proposed rollback closes the entire workspace (`docs/features/herdr-workspace-per-repo/plan.md:130-138`), taking the second agent's tab with it. “Created by this spawn” is not equivalent to “still exclusively owned by this spawn.” The design must either hold an appropriate lock through successful registration/rollback, close only the failed spawn's root tab and tolerate/clean an empty workspace safely, or provide another race-free ownership check. Add an interleaving test where spawn A creates, spawn B reuses and creates a tab, then A fails; B's workspace/tab must survive.

2. **BLOCKER — `UNKNOWN` on the re-list inside the lock still falls through to `workspace create`, defeating both the trichotomy and duplicate prevention.** The outcome table correctly says `UNKNOWN` uses the legacy path (`docs/features/herdr-workspace-per-repo/plan.md:68-77`), but the guarded pseudocode re-resolves and handles only `MATCH`; both `EMPTY` and `UNKNOWN` proceed to creation (`docs/features/herdr-workspace-per-repo/plan.md:106-115`). A transient timeout/malformed response after acquiring the lock can therefore create a duplicate existing workspace. Handle the inner `UNKNOWN` explicitly according to the declared policy and add a test for `EMPTY` initially followed by `UNKNOWN` under the lock. The stated lock-timeout policy also knowingly creates without serialization (`docs/features/herdr-workspace-per-repo/plan.md:118-124`); although the present Herdr launcher is POSIX and this project's `file_lock` blocks indefinitely there (`src/claude_teams/filelock.py:43-59`), the plan should not claim strict duplicate prevention while documenting an unlocked-create fallback.

3. **BLOCKER — The initial `UNKNOWN` legacy branch no longer preserves the existing fresh-server fallback, so “never a failed spawn” is false.** The pseudocode directly returns an unqualified `tab create` for `UNKNOWN` (`docs/features/herdr-workspace-per-repo/plan.md:98-105`). On a fresh server with no active workspace that command raises `workspace_not_found`; today's implementation catches that and creates a workspace (`src/claude_teams/backends/process_manager.py:3023-3050`). The revised branch would propagate the error, contradicting the outcome table's “never a failed spawn” promise (`docs/features/herdr-workspace-per-repo/plan.md:77`) and test 8, which covers only an unqualified create that succeeds (`docs/features/herdr-workspace-per-repo/plan.md:200-202`). Preserve the `_HERDR_NO_WORKSPACE_CODES` catch on the legacy path and route that proven-no-workspace case into the guarded create flow; add `UNKNOWN` plus no active workspace as a test.

4. **SHOULD — The rollback pseudocode names a workspace-id field that is not present in the repository's recorded Herdr response contract.** It says to remember `created.workspace.workspace_id` (`docs/features/herdr-workspace-per-repo/plan.md:113-116`), while the existing observed `workspace_created` fixture carries the id at `root_pane.workspace_id` and has no `workspace` object (`tests/test_backends/test_process_manager_herdr.py:1184-1188`). The normal spawn bookkeeping likewise reads the id from the root pane (`src/claude_teams/backends/process_manager.py:2722-2753`). Specify extraction from `root_pane.workspace_id` (with nonempty-string validation) so the proposed workspace rollback and stored ownership data are implementable against the actual response, and make the new rollback test use the real response shape.

5. **SHOULD — A free-form label cannot safely be interpolated into `_workspace_lock_path` as currently specified.** The override now correctly accepts label characters such as dots and spaces and rejects controls (`docs/features/herdr-workspace-per-repo/plan.md:140-150`), but it still permits path separators and `..`, while the lock is described only as “per session and per label” under the config directory (`docs/features/herdr-workspace-per-repo/plan.md:118-120`). A raw label such as `../other` would escape or alias the intended lock location; very long encoded filenames can also exceed filesystem limits. Require a stable digest or other collision-resistant filename encoding of the normalized label, with the already validated session used only as a safe namespace. Add tests showing labels containing `/`, `..`, spaces, and Unicode map inside the intended lock directory and that identical labels share exactly one lock path.

6. **SHOULD — Resolution parsing remains internally contradictory and does not define mixed-validity listings well enough to avoid duplicate creation.** The plan says only entries with an integer `number` are considered, then says ordering handles “absent numbers” (`docs/features/herdr-workspace-per-repo/plan.md:79-82`); an absent number cannot participate under the preceding rule. It also calls a non-list or a listing where “every entry ... is unusable while the key itself is malformed” `UNKNOWN` (`docs/features/herdr-workspace-per-repo/plan.md:82-84`), but does not say what happens when a well-formed list contains a malformed entry whose `label` matches the requested label alongside valid unrelated entries. Classifying that as authoritative `EMPTY` could create a duplicate. Define this precisely—at minimum, an unusable matching-label candidate must make the result `UNKNOWN`—and add mixed valid/malformed, missing-number, boolean-number, empty-id, and equal-number tests. Test 6 currently covers only ordinary duplicate ordering (`docs/features/herdr-workspace-per-repo/plan.md:194-196`).

7. **SHOULD — Applying the override's rejecting normalizer unchanged to derived folder labels can make a valid spawn fail.** The plan says the Git call/fallback never stops a spawn (`docs/features/herdr-workspace-per-repo/plan.md:60-66`) and that derived labels pass through the same normalizer that rejects leading `-`, controls, and overlength values (`docs/features/herdr-workspace-per-repo/plan.md:142-150`). Repositories and fallback directories can legally have such basenames, so the two promises conflict unless derived invalid characters are transformed or replaced with a safe fallback rather than raising. Specify separate behavior: invalid explicit overrides may raise at construction, while derived labels need deterministic sanitization/fallback that remains nonempty and bounded. Add derived-name cases for a leading dash, control character, and more than 128 characters; current label tests cover only Git/process failures and `/` (`docs/features/herdr-workspace-per-repo/plan.md:184-190`).

8. **NIT — Provenance must distinguish the requested repo label from an unknown active workspace's actual label.** The proposed log fields are `workspace=<id> label=<label>` (`docs/features/herdr-workspace-per-repo/plan.md:152-155`), but the `UNKNOWN` and `-` legacy paths intentionally do not resolve the active workspace label. Logging the derived/override label as though it belonged to the returned workspace would make the diagnostic record misleading. Name it `requested_label`, or log the actual label only when resolution/creation established it; keep the returned `root_pane.workspace_id` as the authoritative workspace id.

9. **NIT — Prior-review accounting:** finding 1 is genuinely resolved by direct creation on authoritative `EMPTY` and routing test 7 (`docs/features/herdr-workspace-per-repo/plan.md:91-116`, `docs/features/herdr-workspace-per-repo/plan.md:197-199`); finding 5 is addressed by adapting `_Herdr` and asserting stored ids (`docs/features/herdr-workspace-per-repo/plan.md:157-164`, `docs/features/herdr-workspace-per-repo/plan.md:194-195`); finding 8 is resolved by the expanded derivation algorithm/tests (`docs/features/herdr-workspace-per-repo/plan.md:50-66`, `docs/features/herdr-workspace-per-repo/plan.md:184-190`); and the documentation half of finding 9 is resolved (`docs/features/herdr-workspace-per-repo/plan.md:165-168`). Findings 2, 3, 4, 6, 7, and the provenance half of 9 are only partially resolved for the reasons above.

Overall verdict: **CHANGES REQUESTED**
