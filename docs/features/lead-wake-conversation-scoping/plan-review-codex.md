# Plan review: lead-wake conversation scoping

## Verdict

**REJECTED**

The nearest-host comparison is a plausible Windows primitive, but the proposed claim lifecycle is not safe in the current call graph. As written, a bystander hook can claim the session for itself, while moving the write to `_persist_session_binding` misses legitimate fast paths. The plan also equates session resolution with ownership, so a benign call from another conversation can steal the claim from the real lead. These are design blockers, not implementation details.

## Findings

1. **BLOCKER — Writing from `_active_session_id` lets the Stop hook claim the session for the bystander it is supposed to reject.** `lead_wake._resolve_session_dir` imports `server_simple` and calls `_active_session_id(create=False)` inside every hook process. Therefore a central “refresh whenever `_active_session_id` resolves” write runs under the hook's ancestry, overwrites `wake-claim-<identity>.json` with the bystander's host PID, and D7 immediately sees a match. The original bug survives. “In the server process” is not an enforceable boundary in the proposed placement because the same module and function run in both entrypoints. **Recommendation:** keep session discovery pure. Add an explicit MCP-server-only claim operation that cannot be reached by `lead_wake` (or add a mandatory `claim=False` path used by the hook), and add an end-to-end regression asserting that resolving a session from `python -m claude_teams.lead_wake` never creates or refreshes the claim.

2. **BLOCKER — Session resolution is not proof of ownership, so the design preserves the same unsafe auto-adoption semantics under a new name.** The plan explicitly accepts `session_info` as an ownership claim. In the current server, `session_info`, `list_agents`, `check_agent`, and similar read paths call `_active_session_id`; a second conversation can cwd+identity auto-adopt the real lead's session and become last writer without spawning or explicitly resuming anything. The real lead then silently loses D3/D5 until it makes another MCP call. That contradicts the stated goal that the owning conversation is the one that “spawned/resumed” the team. **Recommendation:** define ownership-establishing events narrowly: new session creation as part of a team mutation, successful explicit `resume_session`, and the deterministic `AGENT_SESSION_ID` child path. Do not claim on passive discovery or read-only auto-adoption. If first-use adoption must remain, require an explicit resume/lead token or make the binding key conversation-specific before treating it as ownership.

3. **BLOCKER — Neither proposed writer location covers the real session paths correctly.** `_persist_session_binding` is not a common funnel. `_active_session_id` returns immediately when module `_session_id` is already set; spawned agents start with `_session_id = _AGENT_SESSION_ID`; exact-binding recovery returns without persisting; only fallback auto-adopt persists; and `resume_session` persists directly. Conversely, `install_lead_wake(remove=True)` calls `_active_session_id(create=False)` and must not create or refresh ownership merely while removing a hook. **Recommendation:** specify a dedicated `_write_wake_claim(session_id, identity, owner)` API and an exact call-site matrix. Include create, explicit resume, deterministic spawned-child initialization/first MCP request, exact-binding restart behavior, auto-adopt policy, install, remove, external join/read/send, and the hook's own discovery. State whether write failures are best-effort (they should not break an otherwise valid MCP tool call) and how they are logged.

4. **MAJOR — PID equality without a process-start token is vulnerable for the entire session-retention window.** The `ts` field does not bound anything in the proposed algorithm; staleness is described as optional. A recycled `host_pid` can make an unrelated conversation pass D7, especially on Windows, and the repository already uses PID creation tokens elsewhere precisely because bare PIDs are not ownership. `server_pid` does not repair reuse of `host_pid`. **Recommendation:** persist and compare a host creation token/start time (`process_manager.creation_token` on Windows, `/proc/<pid>/stat` start time on Linux) together with PID. Reject a claim unless both match. Define and test a concrete expiry policy only as defense in depth, not as a substitute for the token.

5. **MAJOR — The host/ancestor premise is not yet proven for the supported topology, and the host set is unfinished.** The spike proves that Windows conversations have distinct `claude.exe` processes and that a synthetic/tool-launched walk reaches one. It does not demonstrate, for two simultaneous top-level Claude conversations, that the MCP server and Stop hook for conversation A independently resolve the same nearest host while B resolves a different one. Linux is explicitly unverified. `“the pi host when it exists”` is a placeholder, not a host-set specification, while the plan also calls Codex/pi non-goals. A hard depth of eight can silently disable the real lead under extra launchers (`env`, package shims, shells, containers), and naïve parsing of `/proc/<pid>/stat` breaks on process names containing spaces or parentheses. **Recommendation:** before implementation approval, capture paired server/hook chains for top-level and spawned Claude leads on Windows and Linux. Parse `/proc` robustly (or use `/proc/<pid>/status` plus `/proc/<pid>/comm`), walk to root with cycle detection and a generous safety ceiling such as 64, and enumerate exact tested basenames. If D7 is Claude-only, do not pretend unknown Codex/pi host names are covered: explicitly make them no-claim paths and test that they cannot overwrite a Claude identity's claim.

6. **MAJOR — D7 belongs after D1 and before D2, and progress state must be scoped to the owner generation.** Putting D7 after D2 makes every bystander resolve and lock/read another conversation's `agents.json` before being rejected; a busy registry can therefore delay a bystander Stop even when it eventually allows. More importantly, it cannot undo a claim side effect already performed during D1 resolution. D0 should remain first, D1 should resolve a directory without claiming, then ownership should gate all session reads. D7 must remain before inbox/armed checks and `_apply_guard`, so non-owners write no guard. The existing `wake-progress-<identity>.json` is still shared across owners, however: claim handoff can inherit an old `noprogress_blocks` value and make a newly valid owner hit D6 early. **Recommendation:** place the row as D2 (and renumber later rows) or D1b immediately after session resolution; include the host PID plus creation token/claim generation in the progress schema and reset on owner change. Preserve the invariant that all non-owner/error branches bypass `_apply_guard` and write nothing.

7. **MAJOR — The never-unstoppable failure boundary is underspecified.** “Any error in the walk” is narrower than the new failure surface: claim open/stat/read errors, invalid UTF-8, JSON values of the wrong type, `bool` accepted as an `int`, schema/identity mismatch, atomic replace failure, process exit during inspection, and logging failures all need defined behavior. The current `main` has no outer exception guard around `evaluate`, so one uncaught new exception exits the hook non-zero and violates the stated contract. **Recommendation:** validate exact schema, identity, positive non-boolean PID, host token, and supported host name; contain the complete ownership-read/resolve/compare operation in one fail-open boundary; clean up failed temp files best-effort; and add a final entrypoint-level guard that logs minimally and exits zero with no block output.

8. **MAJOR — The proposed tests miss the failure modes that decide whether the design works.** In particular, hook test 2 says “claim matching an ancestor pid,” but the design requires equality with the **nearest** host; accepting the outer Electron `claude.exe` would recreate cross-conversation matches. The test plan also lacks: (a) proof that hook-side `_active_session_id` cannot write; (b) `_session_id`, `_AGENT_SESSION_ID`, exact-binding, auto-adopt, explicit-resume, install, and remove writer coverage; (c) a two-conversation sequence where A owns, B runs the hook, B makes a passive MCP call, and A remains owner; (d) claim handoff versus stale progress-guard state; (e) PID-reuse/start-token mismatch; (f) malformed scalar/list claims, boolean/negative PIDs, identity/schema mismatch, permission errors, and atomic-write failure; (g) real Windows Toolhelp and real Linux `/proc` smoke tests rather than only a synthetic map; and (h) an automated paired server/hook ancestry test for a spawned nested lead. **Recommendation:** add these as red tests. Make the manual A/B smoke supplemental, not the only production-shaped proof, and assert no stdout block and no claim/guard mutation for B.

9. **MAJOR — Simpler containment at installation time has not been evaluated seriously enough.** Server-spawned Claude agents already use `hooks.write_claude_settings`, producing a per-agent settings file passed with `--settings`; they do not need a shared hook or a disk claim. The risky case is specifically the top-level `install_lead_wake` path writing project/user settings. **Recommendation:** compare, in order: (1) generate a per-session settings file and return a relaunch command for the top-level lead; (2) refuse or require an explicit dangerous opt-in for shared/user installation; (3) bake the installing host PID **and creation token** into the shared hook command, since the install call itself occurs in the owner conversation; and (4) use a bounded transcript-tail ownership marker if compaction behavior can be proven. At minimum, gate `install_lead_wake` on an explicit active session plus a successfully resolved Claude host, never claim on `remove=True`, and document restart/reinstall behavior. The plan should justify accepting the substantially larger cross-platform claim lifecycle only if these narrower options cannot meet the UX requirement.

10. **MINOR — `member_wake` is not automatically isolated from this change because it imports lead-wake guard helpers.** It imports `_apply_guard`, `_scan_senders`, `_is_armed`, and `WakeDecision`. An owner-generation change to the progress schema or helper signature can alter member behavior even if no D7 row is added there. **Recommendation:** keep ownership evaluation out of shared helpers, retain the member guard filename/schema unless intentionally migrated, and run/add member-wake regression tests proving M0-M5 decisions and its no-progress fail-open remain unchanged.
