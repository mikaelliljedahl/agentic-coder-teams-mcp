# Plan review 4 — external-agent-join (final convergence)

**Verdict: APPROVED. Score: 92/100.** V4 resolves the three round-3 blockers at the design level and is implementable. The join replay algorithm now orders reconciliation ahead of expiry, treats expiry only as a new-join gate, refuses left records without touching their markers, and preserves newer valid activity markers (`docs/features/external-agent-join/plan.md:274-313`). The authoritative delivery race now plugs directly into the existing C2 discard machinery, distinguishes newly created from pre-existing rows, and gives `deliver_pending` an observable per-row refusal (`docs/features/external-agent-join/plan.md:329-357`; `src/claude_teams/server_simple.py:4081-4100`, `:4263-4314`). The supported Desktop deployment is honestly scoped to an isolated profile, while recovery keeps external-only sessions discoverable but blocks only fallback auto-adoption (`docs/features/external-agent-join/plan.md:173-187`, `:394-410`; `src/claude_teams/server_simple.py:793-810`). No blocker remains. The minor items below—principally an explicit fail-closed branch for unknown record lifecycle values, wording cleanup in residual-risk/history sections, and precise result-field naming—can be resolved during implementation without changing the approved architecture.

### Join state-machine cross-product

The committed dimensions are ticket status `{open, used, unknown}`, record presence/lifecycle `{absent, running, left, unknown}`, and—only for `open + absent`—expiry `{unexpired, expired}` (`docs/features/external-agent-join/plan.md:279-309`). The resulting audit is:

| Ticket | Record | Expiry | V4 result | Audit |
|---|---|---|---|---|
| `open` | absent | unexpired | Create row, use ticket, ensure marker, success | Dispatched (`plan.md:288-290`). |
| `open` | absent | expired | `invalid_or_expired_token` | Dispatched (`plan.md:291`). |
| `open` | `running` | either | Complete crash A, use ticket, conservative marker repair, success | Dispatched (`plan.md:292-294`). |
| `open` | `left` | either | `membership_revoked/detail:left`, no marker write | Dispatched by any-status rule (`plan.md:298-300`). |
| `used` | absent | n/a | `token_already_used` | Dispatched (`plan.md:301-302`). |
| `used` | `running` | n/a | Re-derive token, conservative marker repair, success | Dispatched (`plan.md:295-297`). |
| `used` | `left` | n/a | `membership_revoked/detail:left`, no marker write | Dispatched by any-status rule (`plan.md:298-300`). |
| unknown ticket status | any normal record state | n/a | `registry_corrupt`, no mutation | Dispatched (`plan.md:303`); implementation should give this check precedence over the any-status-left rule so corruption has one stable answer. |
| `open`/`used` | unknown record status | n/a | Not explicitly stated | Add a final fail-closed `registry_corrupt` branch; non-blocking because it affects only corrupt persisted state and does not alter the normal/crash design. |
| any | duplicate records | n/a | `registry_corrupt`, no mutation | Dispatched before the table (`plan.md:282-286`). |
| any | one record with immutable mismatch | n/a | `registry_corrupt`, no mutation | Dispatched before the table (`plan.md:282-286`). |

The table is complete for every state the feature itself writes. The missing unknown-record-status default is a minor fail-closed specification detail, not a reason to redesign or defer implementation.

## Non-blocking findings

1. **Add an explicit default for corrupt record lifecycle and define precedence.** The plan writes only `running` and `left`, but a detailed fail-closed state machine should say `open/used + record(status not in {running,left}) -> registry_corrupt`. It should also state whether unknown ticket status wins over the “any-status + left” rule; `registry_corrupt` is the cleaner precedence because the ticket store itself is malformed (`docs/features/external-agent-join/plan.md:287-303`). Extend test 11 or add a small corrupt-status parameterization.

2. **Strengthen immutable-record validation slightly.** V4 names `name`, `parent`, and derived digest (`docs/features/external-agent-join/plan.md:282-286`). Also validate `backend == "external"`, `session_id == sid`, `spawned_by == ticket.parent`, and `spawned_by_source == "join_ticket"`; otherwise a corrupt same-`join_ticket_id` non-external row could receive a membership return that `_member_operation` later refuses (`docs/features/external-agent-join/plan.md:165-170`, `:215-227`). This is corrupt-disk hardening, not a normal-path issue.

3. **Define “valid marker” by schema, not merely parseability.** Conservative repair should preserve a valid `running/activity` marker, as test 9 requires, but repair JSON that parses to a dict with an invalid/missing `state`, `event`, or numeric `ts` (`docs/features/external-agent-join/plan.md:304-307`, `:447`; `src/claude_teams/server_simple.py:411-429`). A parseable semantically invalid marker is currently tolerated as absent by state readers, so leaving it would not satisfy the joined-marker contract.

4. **Keep delivery-store failure qualifications in the public contract.** Adding the reason to `_C2_REFUSAL_REASONS` gives the desired success path, but `_release_delivery_claim` and `_discard_delivery_record` can still fail persistence; current code reports/logs those cases rather than falsely promising clean rollback (`src/claude_teams/server_simple.py:3637-3688`, `:3714-3753`, `:4081-4090`). Tool text should say “key reusable when discard persisted” and retain `record_discarded:false` behavior. Add one injected discard-failure assertion to test 20b if practical (`docs/features/external-agent-join/plan.md:342-357`, `:465`).

5. **Do not put `status:"refused"` into the durable delivery-status list.** R4's persisted/public delivery statuses remain exactly `queued`, `delivered`, and `failed` (`src/claude_teams/delivery_store.py:48-60`). Return the new attempt outcome under a clearly separate `refusals` or `results` field, while `deliveries` continues to expose the unchanged pending audit row (`docs/features/external-agent-join/plan.md:348-357`, `:464`; current return at `src/claude_teams/server_simple.py:4310-4314`).

6. **Test 28 should be barrier-based rather than timing-fragile.** A competing `agent_status` cannot finish until `external_read` releases the agents lock, so “within the read's duration” is ambiguous and likely scheduling-sensitive (`docs/features/external-agent-join/plan.md:478`). Use barriers to prove it blocks and then completes after release, with a generous Windows assertion below the 30-second lock deadline (`src/claude_teams/server_simple.py:184`, `:499-508`).

7. **Clean stale v3 wording elsewhere in the plan.** Section 6 still says the secret is “never at rest” despite §0's corrected derivation-input disclosure, and says stale external rows “no longer affect recovery” even though v4 deliberately keeps them discoverable and explicitly adoptable (`docs/features/external-agent-join/plan.md:34-48`, `:483-497`). The file-change list still says “candidacy exclusion,” although v4 leaves `_non_terminal_agents` unchanged and changes only fallback auto-adoption (`docs/features/external-agent-join/plan.md:425-431`, `:173-187`). Section 8's historical B6 disposition likewise describes the superseded v3 exclusion (`docs/features/external-agent-join/plan.md:503-521`). Update these to “does not trigger silent fallback auto-adopt” and label the old table superseded so implementation does not follow stale text.

8. **Profile isolation remains an empirical release note, not a repository-verifiable fact.** The scoped design is acceptable because it explicitly branches on the smoke result, but `implementation.md` must record the tested Desktop version/profile/config behavior and README/INSTALL must select exactly one of “isolated supported” or “isolation unavailable on this client” (`docs/features/external-agent-join/plan.md:394-409`).
