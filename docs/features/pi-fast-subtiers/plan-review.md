# Independent plan review

1. **F1 — required: The proposed “same capability, materially faster” contract wording hides a material context downgrade.**

   Evidence: the plan calls both additions the “same capability, less latency” sibling of the preceding tier (`docs/features/pi-fast-subtiers/plan.md:23-25`) and directs the only client-visible contract to use that framing (`docs/features/pi-fast-subtiers/plan.md:49-52`). The current contract tells callers to choose by task capability and says tiers never silently downgrade (`src/claude_teams/server_simple.py:3163-3181`). However, the live Pi catalog reports Terra at 272K and Sol at 372K, while Luna is 1M; therefore `medium-fast` loses roughly 73% of the context available from `medium`, and `high-fast` loses roughly 63% relative to `high`. The plan acknowledges the latter only outside the consuming-agent contract (`docs/features/pi-fast-subtiers/plan.md:12-14`) and does not acknowledge the former. Availability validation cannot protect callers from this distinction: it checks only model-id membership and returns the selected pair (`src/claude_teams/backends/pi.py:249-260`), while discovery itself retains only model ids and discards context metadata (`src/claude_teams/backends/pi.py:139-150`).

   Recommended change: revise the plan and required `spawn_agent` wording to describe the fast tiers as benchmark/compute-capability alternatives with smaller context windows, explicitly naming Terra 272K and Sol 372K versus Luna 1M and advising callers not to choose them for context-heavy tasks. Avoid the unqualified phrase “same capability.” Apply the same qualification in the README and Pi ladder comment. The selected pairs themselves are technically launchable and preserve the existing “missing tier model hard-errors” behavior; the problem is the proposed selection contract, not `resolve_launch`.

2. **F2 — required: `CLAUDE.md` is missing from “files affected” even though it enumerates the tier vocabulary and states obsolete Pi semantics.**

   Evidence: the plan claims the ladder is documented in four places and lists only `pi.py`, the server docstring, README, and `ADDING-A-BACKEND.md` (`docs/features/pi-fast-subtiers/plan.md:58-63`, `docs/features/pi-fast-subtiers/plan.md:79-80`). `CLAUDE.md:111-114` separately says model tiers are `low/medium/high/xhigh/ultra` and that Pi soft-falls back to its CLI default. Both statements already disagree with actual code: Pi advertises `cheapest` through `max` (`src/claude_teams/backends/pi.py:186-208`) and hard-errors for an unavailable tier (`src/claude_teams/backends/pi.py:249-260`). Adding two more tier names while leaving this backend-change guidance untouched increases the contradiction.

   Recommended change: add `CLAUDE.md` to “files affected” and update its backend-tier summary to distinguish the six shared Codex/Pi tiers, Pi-only `medium-fast`/`high-fast`, hard failure for unavailable tier models, and Pi's soft fallback only for unavailable raw slugs. No change is needed in `docs/reference/agent-messaging-protocol.md`: its spawn section describes mechanical resolution but does not enumerate tier names (`docs/reference/agent-messaging-protocol.md:150-177`).

3. **F3 — required: The test plan does not protect the only contract the consuming agent reads.**

   Evidence: the plan correctly identifies the `spawn_agent` docstring as the sole consuming-agent contract (`docs/features/pi-fast-subtiers/plan.md:49-52`) but proposes tests only in `tests/test_backends/test_pi.py` and relies on the unchanged Codex list test (`docs/features/pi-fast-subtiers/plan.md:82-99`). The repository already provides `_registered_description`, which reads the actual FastMCP `Tool.description` rather than merely `func.__doc__` (`tests/test_tool_descriptions.py:131-142`), yet its current spawn test checks only the permission-mode text (`tests/test_tool_descriptions.py:145-155`). Thus an implementation could update the wrong text, omit the Pi-only qualification/context warning, or later regress the registered contract while all proposed backend tests remain green.

   Recommended change: add `tests/test_tool_descriptions.py` to “files affected” and add a registered-description assertion that `spawn_agent` exposes both exact hyphenated names, marks them Pi-only, gives their model/effort pairs, and states their smaller context-window trade-off. This also exercises the hyphenated strings at the actual MCP contract boundary.

4. **F4 — nice-to-have: The ladder-invariant rewrite is logically sound, but its intent should include shared-order preservation explicitly.**

   Evidence: the proposed rewrite requires a strict key superset, shared-pair differences only at `high`, and exactly the two extra keys (`docs/features/pi-fast-subtiers/plan.md:67-70`). The current draft test implements those set/pair checks (`tests/test_backends/test_pi.py:154-165`), while the exact Pi list assertion pins all eight positions (`tests/test_backends/test_pi.py:99-109`) and the unchanged Codex test pins its six positions (`tests/test_backends/test_codex.py:69-79`). Together these tests are sufficient, and broad search found no production code that indexes a tier, assumes length six, sorts this list, or splits model input on `-`; `supported_models()` simply exposes dictionary insertion order (`src/claude_teams/backends/pi.py:199-208`), and CLI/MCP listing consumes an arbitrary list (`src/claude_teams/cli.py:94-119`, `src/claude_teams/server_simple.py:6255-6269`).

   Recommended change: for a more local invariant, have the rewritten cross-backend test also assert that filtering Pi's keys to Codex's key set yields `list(codex_ladder)`. This is not required for correctness because the two exact-list tests already imply it. No production change to Codex, CLI, registry, hooks, or normalization is indicated.

5. **F5 — nice-to-have: Resume/follow-up is safe because records store concrete launch values, but the plan should record and preferably test that invariant.**

   Evidence: `spawn_agent` resolves the caller's tier before constructing the request (`src/claude_teams/server_simple.py:3258-3263`) and persists the resulting concrete slug and bundled effort, not the tier name, in `agents.json` (`src/claude_teams/server_simple.py:3300-3312`, `src/claude_teams/server_simple.py:3323-3340`). Follow-up request construction deliberately reuses those stored concrete values without calling `resolve_launch` again (`src/claude_teams/server_simple.py:3937-3946`, `src/claude_teams/server_simple.py:3983-3997`), and Pi resume emits them through the same `_model_args` path (`src/claude_teams/backends/pi.py:354-374`, `src/claude_teams/backends/pi.py:448-466`). Consequently, new spawns using either fast tier resume as the exact original slug/effort; ladder remaps and later catalog discovery do not silently substitute another model. A hypothetical hand-edited/legacy record containing `"medium-fast"` would be treated as a raw model id on resume, but no released version could have persisted that new tier, and the normal spawn path never persists tier names.

   Recommended change: add a plan note that follow-up intentionally does not re-resolve stored models. Prefer one focused server-path regression showing a Pi fast-tier spawn record contains `gpt-5.6-terra`/`high` (or `gpt-5.6-sol`/`medium`) and that `_build_resume_request` carries those concrete values unchanged. This is defense-in-depth rather than a required production change.

VERDICT: CHANGES REQUIRED
