# Implementation review: harden exiting-child test

## Verdict: APPROVED WITH CHANGES

1. **Plan-review findings 2–5 are implemented correctly.** The test repoints the stored record to the fixture child's `pid` and `create_token` before taking the `before` snapshot (`tests/test_follow_up_delivery.py:290-294`), rather than special-casing PID 123. `_pin_liveness_to` captures the original bound `health_check` before monkeypatching, asserts that every probe uses the expected handle, and delegates with the child's token (`:256-263`). The fixture asserts a truthy token before reaping (`:129-133`). `git diff dda9d5b^ dda9d5b -- src` is empty, so there is no production change. The revised plan also correctly limits the untracked post-resume PID issue to this fake backend and no longer presents it as a demonstrated built-in-backend defect.

2. **The token acquisition is deterministic on both supported CI platforms.** The child blocks in `sys.stdin.read()` while the parent retains the write end of a pipe, so it cannot exit before the token read. On Linux, `Popen` has returned a live PID and `/proc/<pid>/stat` exposes its start time. On Windows, `CreateProcess` has returned a live child owned by the test process, and `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` plus `GetProcessTimes` can read its creation FILETIME. Only after that read does the fixture close stdin and wait for termination. The fixture then returns without retaining the `Popen`, so CPython releases its Windows process handle before the test's liveness probes. Thus the captured identity is available before exit, and later PID reuse cannot satisfy the token comparison.

3. **The test is not tautological and still guards the settle-window branch.** The wrapper fixes process identity; it does not return a hard-coded liveness value or delivery reason. The original `health_check` observes the terminated process, the real scanner finds no receipt, and `confirm_delivery()` sees death at elapsed time zero. The asserted `resume_not_confirmed` is selected only by `delivery.py`'s `elapsed < settle_s` branch. If immediate death were instead classified as the late-death `not_delivered` case, line 299's reason assertion would fail. The existing later-death test separately exercises the other side of the boundary. The focused test passed in this worktree (`1 passed`).

4. **Finding 6 is substantively covered but its evidence is not durable.** The implementation has the required non-`None` token assertion, original-method capture, and unexpected-handle assertion. `plan.md` and `implementation.md` report scratch red runs for both the live original PID (`agent_busy`) and a recycled post-resume PID (`delivery_unconfirmed`), plus a green simulated-reuse run. Those runs satisfy the requested “test/run,” but they are neither committed nor reproducible from the commit, so a future reader can only trust the narrative. This is not a blocker because the committed test directly prevents ambient-handle probing, but a small committed regression test or documented command/helper would make finding 6 independently repeatable.

5. **The fixture should reap the child in a `finally` block.** At present, a token-read exception or the token assertion failing occurs before stdin is closed and before `wait()`. Exception unwinding will normally close the pipe and let the child exit, but the fixture no longer guarantees it is reaped on its failure path. Wrap token acquisition/assertion in `try/finally` that closes stdin and waits (with a bounded terminate/kill fallback if appropriate). This does not affect the normal Linux/Windows determinism, but it avoids leaving a child/zombie precisely when the platform assumption under test fails.

6. **The revised documentation still contains stale and misleading text.** `plan.md:41-44` repeats the “keep a real process” introduction. More importantly, `plan.md:76` says the `"123"` sentinel is duplicated and kept consistent with `_dead_agent`, even though the accepted design explicitly removed all PID-123 special-casing from this test. Remove that obsolete risk. The fixture docstring and plan also say the token “is unreadable” once the process is gone; that is too absolute on Windows, where creation time can remain readable briefly while a process-object handle is retained. Say that the token must be captured while liveness is guaranteed and may become unreadable after exit. Finally, `implementation.md:40` says findings 2–5 were adopted even though its own red/green section is intended to satisfy finding 6; either say findings 2–6 or explicitly state that finding 6 is supported only by uncommitted scratch runs.

7. **No other functional defect is evident in commit `dda9d5b`.** Record preservation is checked after the real follow-up path, resume execution is asserted, the pending marker must remain absent, and the wrapper is narrow enough that a new or unexpected production probe will fail the test rather than be silently stubbed. The requested change remains test-scoped.
