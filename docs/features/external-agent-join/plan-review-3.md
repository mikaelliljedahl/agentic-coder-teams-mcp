# Plan review 3 — external-agent-join (token-carried design)

**Verdict: NOT READY. Score: 74/100.** V3 is substantially stronger: it closes the public full-list credential leak, defines a genuinely cross-process member-operation critical section, fixes the two originally identified marker/write crash windows in the normal running-member case, places delivery guards at the correct early call sites, and adds a serious test matrix (`docs/features/external-agent-join/plan.md:27-44`, `:199-232`, `:251-307`, `:370-412`). Three design issues remain blocking. First, reconciliation still rejects an expired-open ticket before consulting the crash-recovery record and replays a used ticket over a `left` record by rewriting its marker to `running/joined` (`docs/features/external-agent-join/plan.md:256-274`). Second, the authoritative delivery-race refusal has no specified cleanup/settlement for the durable row that `_guaranteed_send` already created, while current rollback recognizes only three C2 reasons (`src/claude_teams/server_simple.py:4047-4069`, `:4083-4100`). Third, the proposed Desktop setup registers the restricted server alongside the unrestricted main server in the same conversation, so prompt choice remains the only thing preventing ambient root-tool use; additionally, excluding all external records from `_non_terminal_agents` makes an external-only team undiscoverable to a legitimate lead after an exact binding miss (`docs/features/external-agent-join/plan.md:169-175`, `:330-348`; `src/claude_teams/server_simple.py:649-704`, `:763-810`). The plan is ready after those state-machine, delivery-row, and containment/recovery issues are specified and covered by tests.

## Blockers (must fix)

1. **Complete the join reconciliation state machine for expiry and revocation.**
   - The numbered algorithm checks `expired-open` before its “record lookup FIRST” step (`docs/features/external-agent-join/plan.md:253-260`). A process can save the external row, crash before saving the ticket, and remain down past the 24-hour TTL; the retained ticket is then expired-open plus a valid matching record, but replay returns `invalid_or_expired_token` rather than completing crash A (`docs/features/external-agent-join/plan.md:146-157`, `:262-268`). That leaves a ghost row/name reservation outcome with no recoverable returned credential.
   - A used ticket with any matching record currently follows the marker-repair path without checking lifecycle status (`docs/features/external-agent-join/plan.md:269-274`). After `leave_team` sets status `left` and marker `waiting/left`, replaying the retained join credential re-derives the token and overwrites the marker as `running/joined`; membership calls still reject because status remains left, so public liveness and authority disagree (`docs/features/external-agent-join/plan.md:169`, `:194-197`, `:230-232`, `:398-399`).
   - **Required change:** locate the ticket, then locate/validate duplicate records before applying expiry. Dispatch at least on `(ticket status, record presence, record lifecycle)`: expired-open+no-record is invalid; expired-open+one exact matching running record completes crash A (or performs a separately specified safe cleanup); used/open+matching `left` returns `membership_revoked/detail=left` and never rewrites the marker; used+running repairs only a missing/corrupt joined marker and must not clobber a newer valid activity marker. Define the failure for immutable-field mismatch and unknown ticket status. Add exact tests for expired crash A, replay after leave, replay after kill, and an existing activity marker (`docs/features/external-agent-join/plan.md:256-274`, `:383-386`).

2. **Specify durable-row cleanup/settlement for the authoritative external-target race.**
   - In direct follow-up, the authoritative `_prepare` recheck occurs only after `_open_delivery_record` has created and claimed a row (`src/claude_teams/server_simple.py:4047-4069`). The current finally block releases the claim, but a newly created row is discarded only when the returned reason is in `_C2_REFUSAL_REASONS`; that set contains `not_spawner`, `parent_unknown`, and `stale_authorization`, not `external_agent_pull_only` (`src/claude_teams/server_simple.py:4083-4100`). V3 does not say to add the new reason, discard the row, or settle it terminally (`docs/features/external-agent-join/plan.md:302-307`). A surviving pending row consumes the idempotency key and will be refused by every future drain.
   - `deliver_pending` currently discards its per-attempt `results` and returns only an attempted count plus the store's public rows, so “deliver_pending refuses `external_agent_pull_only`” also needs an exact public response contract (`src/claude_teams/server_simple.py:4284-4314`; `docs/features/external-agent-join/plan.md:299-301`, `:400`).
   - **Required change:** define the authoritative direct-race result as a C2 no-side-effect refusal and add `external_agent_pull_only` to rollback (or an equivalent explicit discard path) when this call created an unsent row. For a pre-existing pending row, release any claim and return a stable non-mutating refusal without changing the audit row. Specify how `deliver_pending` exposes that refusal. Extend test 20 to byte-compare the direct prepare-race store, assert the idempotency key remains reusable as intended, assert no `active_holder` survives, and assert the exact drain result (`docs/features/external-agent-join/plan.md:400`).

3. **Make EXTERNAL_ONLY actual client isolation, and preserve legitimate lead discovery.**
   - The restricted process is useful, but the documented configuration leaves the unrestricted main server in the same conversation; v3 explicitly admits this (`docs/features/external-agent-join/plan.md:330-346`). The model can still choose `win-agent-teams.send_message`, `list_agents`, or `kill_agent`, and only the prompt tells it not to. Thus the described deployment does not satisfy round 2's requirement for an external-only endpoint/profile where ambient tools are absent from the client surface (`docs/features/external-agent-join/plan-review-2.md:51-52`). Test 26 proves one server's registration set, not that the QA client lacks the other server (`docs/features/external-agent-join/plan.md:411`).
   - Excluding external rows from `_non_terminal_agents` is contained in code but not safe in product semantics. That helper feeds `_candidate_sessions`; candidates feed both auto-adoption and the recovery nudge/session-info list (`src/claude_teams/server_simple.py:649-704`, `:793-810`, `:4580-4609`). If the lead's parent id changes and its exact binding misses, a session with one active external member becomes invisible even though the lead must recover it to send, inspect, leave, or kill that member. Test 22 asserts the loss rather than testing legitimate recovery (`docs/features/external-agent-join/plan.md:407`). “External is not backend-resumable” does not imply “the containing team session is not recoverable.”
   - **Required change:** make the supported setup a separate Desktop profile/process/config in which the main server is absent, or otherwise provide enforceable client/request-scoped denial; if Desktop cannot do that, make isolation an explicit release prerequisite rather than calling the dual-entry setup a technical containment control. Separately split “session discoverable/addressable” from “backend resumable/auto-adoptable” instead of removing external-only sessions from `_candidate_sessions` wholesale. At minimum, keep them in `recoverable_sessions` for explicit `resume_session`, and define whether automatic adoption is allowed. Add tests for a legitimate lead recovering an external-only team after exact-binding miss and for the actual client-visible tool set in the supported Desktop deployment (`docs/features/external-agent-join/plan.md:169-175`, `:322-348`, `:410-411`).

## Non-blocking findings

1. **The at-rest claim overstates what the digest design buys.** `join-tickets.json` retains both `ticket_id` and `ticket.token`, and the derivation is an unkeyed public SHA-256 formula, so a reader of that file reconstructs the exact member secret (`docs/features/external-agent-join/plan.md:38-44`, `:137-150`). This is acceptable only because filesystem readers are explicitly out of threat scope; describe it as “no member secret in `agents.json` and no tool-level disclosure,” not “secret never at rest” (`docs/features/external-agent-join/plan.md:41-44`, `:425-426`). A server-keyed HMAC would protect against ticket-store disclosure, but would introduce key persistence/recovery requirements and is not necessary under the stated threat model.

2. **The global registry lock can create long stalls.** `_read_inbox` reads and groups the whole append-only inbox before advancing the cursor (`src/claude_teams/server_simple.py:2551-2629`), and v3 holds the session-wide agents lock throughout (`docs/features/external-agent-join/plan.md:217-224`). On Windows, contenders time out after 30 seconds; on POSIX, `flock` blocks without that deadline (`src/claude_teams/server_simple.py:184`, `:486-504`; `src/claude_teams/filelock.py:32`, `:43-58`). This does not create a lock cycle, but it can make spawn/kill/status/ticket operations fail or stall behind a large read. Document the platform behavior and add a bounded large-inbox contention test; a dedicated per-reader cross-process lock plus a short agents-lock validation protocol would be preferable if revocation linearizability can be retained.

3. **Conditional FastMCP registration is feasible but broader than the plan suggests.** The current module registers every tool at decoration time (`src/claude_teams/server_simple.py:2233`, `:2411`, `:2493`, `:2661`, `:4102`, `:4155`, `:4245`, `:4411`, `:4515`, `:4567`, `:4658`, `:4752`, `:4795`, `:4844`, `:4911`). Implementing external-only mode therefore requires replacing or wrapping all registrations, not merely adding a condition near the new tools. The installed FastMCP version supports decorator/direct conditional registration, so no framework blocker was found; however, registered descriptions are captured at decoration time and `_with_disk_note` has an explicit ordering requirement (`src/claude_teams/server_simple.py:1176-1184`; `tests/test_tool_descriptions.py:130-142`). Test both registered names and client-visible descriptions in each mode. Desktop's actual namespace/profile behavior cannot be verified from this repository.

4. **The cursor parity test should cover the full advertised validation contract.** Test 14 covers the main successful modes but not `since_seq` without `from_agent`, negative `limit`, `full=True` ignoring limit, multi-sender global ordering, exact `unread_count`/`has_more`, or `limit=0` cursor-file byte stability (`docs/features/external-agent-join/plan.md:394`; `src/claude_teams/server_simple.py:2494-2532`, `:2571-2655`). These are refactor-regression tests rather than new design blockers.

5. **Revocation races are not yet “both directions.”** Test 18 includes kill versus send/read and leave versus send, but not leave versus read (`docs/features/external-agent-join/plan.md:398`, `:450`). Add that barrier case and assert a second leave does not rewrite the marker, as test 19 already does sequentially (`docs/features/external-agent-join/plan.md:399`).

6. **The fixed-fence injection claim needs escaping or a narrower statement.** A note containing the fixed closing delimiter can terminate its own block because v3 inserts it verbatim (`docs/features/external-agent-join/plan.md:241-244`). Since the lead authored the note, this is not an authorization boundary, but test 1 should include delimiter text if the plan keeps the “cannot alter” claim (`docs/features/external-agent-join/plan.md:376`).

7. **Update the full-list contract wording when sanitizing it.** The current docstring promises the raw registry record (`src/claude_teams/server_simple.py:4663-4667`). After `_public_agent_record`, it should say “sanitized registry fields” and explicitly reserve credential omission; otherwise the implementation would correctly redact but violate its published schema (`docs/features/external-agent-join/plan.md:309-314`).
