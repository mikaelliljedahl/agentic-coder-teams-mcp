# Plan review 1 — external-agent-join

**Verdict: not ready to implement. Score: 42/100.** The plan correctly identifies the three main PRD corrections, especially the need to bypass resumable delivery and PID termination for external agents. However, its highest-risk mechanism—post-import process-global identity mutation—is not made atomic against FastMCP's concurrent worker threads, its eligibility test can be bypassed by existing session state and raw environment state, and the claimed restart-safe deferral is false in a same-cwd recovery scenario. Ticket/name transactions, deregistration, and stale delivery paths also have correctness holes. These are design blockers, not implementation details.

## Blockers (must fix before implementation)

1. **The identity rebind is not atomic with respect to tool calls; the GIL argument is insufficient.**
   - **Problem:** The plan says individual global reference swaps are atomic and therefore treats assignments to `IDENTITY`, `_AGENT_PARENT_NAME`, `_session_id`, and `_JOINED_EXTERNAL` as a safe rebind (`docs/features/external-agent-join/plan.md:178-185`). FastMCP tool bodies run blocking work in worker threads (`src/claude_teams/async_utils.py:7-21`), and the server already documents this concurrency for `read_messages` (`src/claude_teams/server_simple.py:440-445`). Existing tools also split their observations: `send_message` captures `_active_session_id()` before dispatching work (`src/claude_teams/server_simple.py:2440-2442`) but reads `IDENTITY` later inside the worker when stamping the line (`src/claude_teams/server_simple.py:2475-2481`); `read_messages` similarly captures the session first (`src/claude_teams/server_simple.py:2540-2542`) and reads `IDENTITY` later (`src/claude_teams/server_simple.py:2551-2553`). A concurrent join can therefore combine the old session with the new identity, or the new session with the old root identity. Atomicity of each assignment does not make the multi-field transition or these multi-step tool calls atomic.
   - **Completeness of globals:** `_AGENT_PARENT_NAME` is indeed required by `_spawner_target` (`src/claude_teams/server_simple.py:1021-1027`), and `_session_id`/`IDENTITY` are required. `_AGENT_NAME` has no post-import reader (`src/claude_teams/server_simple.py:119`), so it need not be mutated. `_AGENT_SESSION_ID`, however, remains an immutable recovery-precedence input (`src/claude_teams/server_simple.py:763-783`) and must be accounted for by eligibility/recovery policy. `_pending_recovery` is also mutable cached state (`src/claude_teams/server_simple.py:245-250`, `763-810`) and must be cleared or it can annotate a post-join result with a stale root recovery nudge. `_binding_key` and `_candidate_sessions` dynamically read `IDENTITY`, so they are not stale caches (`src/claude_teams/server_simple.py:462-472`, `649-690`), but they become race participants during the transition.
   - **Suggested fix:** Introduce one process-wide identity/session state object and a process-wide lock. Every identity-bearing tool must acquire the lock before resolving/capturing session and hold it through all uses of identity/session; `join_team` must take it exclusively before eligibility preflight and hold it through ticket claim, registry write, marker write, and rebind. At minimum, serialize the complete bodies of `spawn_agent`, send/read, follow-up/delivery tools, kill/leave, create/join, resume/session recovery, and status tools against rebind. Add deterministic barrier-based concurrency tests proving no call can observe a mixed identity/session snapshot. Clear `_pending_recovery` as part of the committed transition.

2. **The eligibility guard does not close the #24-adjacent hijack/orphaning surface.**
   - **Problem:** The proposed guard only checks unresolved status, `IDENTITY == "team-lead"`, and whether the current `_session_id` has a record with `spawned_by == IDENTITY` (`docs/features/external-agent-join/plan.md:284-296`). A blank `AGENT_NAME` with a non-empty `AGENT_SESSION_ID` but no `WIN_AGENT_TEAMS_SESSION_DIR` still resolves as a legitimate `team-lead`, because `_resolve_identity` only uses `WIN_AGENT_TEAMS_SESSION_DIR` as its spawned signal (`src/claude_teams/server_simple.py:137-157`); `_session_id` is then pre-populated directly from that raw environment value (`src/claude_teams/server_simple.py:345`). If the referenced registry is empty or contains only “foreign” children, the proposed test allows join. Likewise, a root process may already have an exact binding or auto-adoptable session while `_session_id` is still empty; `_recover_session_id` can discover it (`src/claude_teams/server_simple.py:763-805`), but the planned guard only examines `_session_id`. Conversely, a benign status/read call can set `_session_id` through `_active_session_id` (`src/claude_teams/server_simple.py:841-858`), after which the guard still allows abandoning any session that happens not to contain an own child, despite the PRD requiring no bound session “with activity.”
   - **Race:** The eligibility preflight is outside the ticket transaction, and the plan explicitly allows the authoritative `_assume_identity` to fail after the ticket and agent record have been written, leaving both in place (`docs/features/external-agent-join/plan.md:254-269`). A concurrent spawn can create a child between preflight and rebind. The result would be a consumed ticket plus a ghost external record, while the process remains root.
   - **Suggested fix:** Define “fresh external joiner” from immutable import provenance, not mutable `IDENTITY` alone: require no raw `_AGENT_NAME`, `_AGENT_SESSION_ID`, `_AGENT_PARENT_NAME`, or spawned signal; require `_IDENTITY_UNRESOLVED is False`; require `_session_id == ""`; and reject an exact process binding/session activity. Decide explicitly how a first-call join avoids cwd fallback without authorizing an already-active root. Run the authoritative check once under the process identity lock immediately before all side effects. If a later durable step or rebind fails, perform an explicit recoverable rollback/claim protocol; never leave an external registry row for a process that did not assume it. Add tests for raw `AGENT_SESSION_ID`, each raw `AGENT_*` combination, exact binding, auto-adopt candidate, a prior benign read, and a spawn racing join.

3. **The claimed restart-safe deferral is not safe in the same-cwd case.**
   - **Problem:** It is correct that a binding persisted after rebind would be keyed by the child identity and would not be found when a restart imports as `team-lead`: `_binding_key` includes current `IDENTITY` (`src/claude_teams/server_simple.py:462-472`). It is also correct that writing a root-keyed positive binding to the lead's session would be dangerous. But “write no binding” does not prove the restarted process cannot adopt the session. Session creation already persisted the real lead's `team-lead` binding (`src/claude_teams/server_simple.py:1931-1937`). `_candidate_sessions` ignores parent PID and accepts any binding with matching identity and cwd whose registry contains a non-terminal record (`src/claude_teams/server_simple.py:649-690`); `running` external records are non-terminal because only `killed` is terminal (`src/claude_teams/server_simple.py:186`, `693-704`). `_recover_session_id` auto-adopts a single such candidate when auto-adopt is enabled (`src/claude_teams/server_simple.py:793-805`). Therefore, if Desktop's server cwd matches the lead's cwd, a restarted external process importing as `team-lead` can silently adopt the lead's session even though join persisted no binding.
   - **Additional recovery hazard:** A non-empty raw `_AGENT_SESSION_ID` wins before the unresolved-identity check in `_recover_session_id` (`src/claude_teams/server_simple.py:773-780`), so restart safety also depends on immutable launch environment, not just join bindings. A joined external can currently call `resume_session`, which writes a child-identity binding and `_prune_superseded_bindings` removes other bindings to the same session (`src/claude_teams/server_simple.py:615-630`, `4516-4553`), potentially deleting the real lead's recovery binding.
   - **Suggested fix:** Replace the proposed weak test with worst-case tests that leave the real lead binding in place, use the same identity and cwd, vary parent IDs, enable auto-adopt, and exercise raw `AGENT_SESSION_ID`. Design an explicit negative/tombstone join binding that recovery recognizes as “do not auto-adopt as root,” or otherwise change recovery so a process that previously joined externally cannot silently become root. Prevent joined external identities from `resume_session`/binding persistence, or make binding pruning ownership-aware. If a stable per-Desktop-process key cannot be recovered across restart, state that safe restart detection is unsolved and block v1 rather than claim safety.

4. **Leaving or killing an external record does not revoke the already-rebound process's messaging authority.**
   - **Problem:** `send_message`'s upstream alias path does not verify that the caller has a registry record: aliases resolve directly to `_spawner_target` before registry lookup (`src/claude_teams/server_simple.py:1049-1056`), and the tool appends using the process-global identity (`src/claude_teams/server_simple.py:2475-2485`). `read_messages` likewise reads solely from `inbox-{IDENTITY}` (`src/claude_teams/server_simple.py:2540-2553`). Thus, after the lead removes the external record, the still-running joined process can continue sending as the child and calling other team tools. This contradicts AC6's requirement that subsequent calls report that it is no longer registered (`docs/features/external-agent-join/PRD.md:267-269`), and the matrix does not test that part (`docs/features/external-agent-join/plan.md:372`).
   - **Leave is also not a real inactive state:** The plan leaves `_JOINED_EXTERNAL` true and merely marks the record `completed` (`docs/features/external-agent-join/plan.md:321-325`). Current recipient classification ignores status and only checks `spawned_by` (`src/claude_teams/server_simple.py:1063-1073`), so the planned backend-only external branch would continue appending messages to a child that has left. `completed` is not in `_TERMINAL_STATUSES` (`src/claude_teams/server_simple.py:186`), so it also remains a recovery candidate.
   - **Suggested fix:** Model external membership as an explicit runtime state (`active`, `left`, `deregistered`) and add a registry-backed `_require_active_external_membership` gate to every identity-bearing/mutating team tool. It should verify name, session, backend, active status, PID, and creation token. Never revert to `team-lead` in-process after leave—that would create the exact masquerade risk—but return `external_agent_left`/`external_agent_deregistered`. Make lead-to-external delivery require an active record, add `completed` to the terminal/recovery policy or remove the record, and specify cleanup semantics. Test send/read/spawn/create-ticket after leave and after kill, plus lead send to a left child.

5. **The ticket/name store is serialized but not transactionally correct.**
   - **Name reservation:** Sharing `_agents_file_lock` is not enough to reserve a name against later spawns. `spawn_agent` currently computes `_unique_agent_name(name, agents)` using only `agents.json` while holding that lock (`src/claude_teams/server_simple.py:2293-2296`). After ticket creation releases the lock, a spawn can legally take the ticket's reserved name because it never reads open tickets. The plan's test only checks ticket creation against existing agents/tickets (`docs/features/external-agent-join/plan.md:359-361`), not spawn-after-ticket.
   - **Two-file durability:** Current registry saving is a direct `write_text`, not atomic replace (`src/claude_teams/server_simple.py:518-519`). The plan does not define atomic-save/error semantics for `join-tickets.json`, nor a crash-consistent protocol for updating ticket status and appending the agent across two files (`docs/features/external-agent-join/plan.md:233-247`, `258-269`). A crash or write failure can leave either an open token with an inserted agent (reusable) or a used token with no agent (lost join). The proposed “roll nothing back” disposition explicitly accepts part of this inconsistency (`docs/features/external-agent-join/plan.md:267-269`).
   - **Retention conflict:** `create_join_ticket` prunes `used` tickets (`docs/features/external-agent-join/plan.md:243-245`), but the API promises a distinct `token_already_used` result (`docs/features/external-agent-join/plan.md:362-363`). After any later ticket creation, reuse of the old token can no longer produce that result. No used/expired retention or audit policy is specified.
   - **Unsafe names:** `_unique_agent_name` does not validate safe characters and does not truncate a non-colliding first candidate (`src/claude_teams/server_simple.py:543-557`), while the new marker/inbox paths interpolate the name directly (`src/claude_teams/server_simple.py:364-375`). Spawned backends eventually enforce a 1–64 safe-name regex in hook wiring (`src/claude_teams/hooks.py:38-47`), but an external record bypasses backend launch validation.
   - **Suggested fix:** Make spawn consult open ticket reservations under the same lock (and add spawn-after-ticket/ticket-after-spawn concurrency tests). Use atomic replace for each store and specify a recoverable claim/journal protocol across ticket and agent writes, with a stable ticket ID/digest on the external record so retries reconcile rather than duplicate. Retain used token digests long enough to return `token_already_used`; prune expired-open and old-used rows under a documented retention policy. Validate names against the shared safe-name invariant before writing any ticket or path.

6. **The external inbox branch is necessary but not sufficient, and its proposed lookup is racy.**
   - **Problem:** The correction is directionally right: a `RECIPIENT_CHILD` currently always calls `_guaranteed_send` (`src/claude_teams/server_simple.py:2446-2461`), while upstream appends to an inbox (`src/claude_teams/server_simple.py:2475-2485`). However, the plan proposes classifying and then separately fetching the target record (`docs/features/external-agent-join/plan.md:274-283`). `_classify_recipient` already performs a separately locked registry read (`src/claude_teams/server_simple.py:1030-1073`). Between classification, the second fetch, and append, kill/leave/name reuse can change the target; an acknowledged write can land in a removed or same-named successor's inbox, or race cleanup.
   - **Missed delivery call site:** The planned `_guaranteed_send` refusal covers new `send_message`/`follow_up_agent` calls, but `deliver_pending` calls `_guaranteed_delivery` directly for durable pending rows (`src/claude_teams/server_simple.py:4245-4259`, `4261-4319`). A stale pending row for a name later reused by an external agent therefore bypasses the planned `_guaranteed_send` check and falls into backend preparation. `_guaranteed_delivery` will eventually return generic `backend_not_supported` when `registry.get("external")` fails (`src/claude_teams/server_simple.py:2940-2959`, `3020-3032`), not the promised `external_agent_pull_only`, and it may mutate delivery claim state first.
   - **Reason precedence:** `_guaranteed_send` validates the idempotency key before preflight (`src/claude_teams/server_simple.py:3997-4034`). An external check “after `_preflight_refusal`” as planned cannot produce `external_agent_pull_only` for a keyless `follow_up_agent` unless validation ordering or a tool-level preflight changes; the matrix's invocation does not specify a valid key (`docs/features/external-agent-join/plan.md:373`).
   - **Suggested fix:** Resolve and validate the active external record under one registry transaction and serialize the inbox append against leave/kill/name reuse. Return a record generation/create token from classification or perform a single authoritative helper rather than two unlocked reads. Add an external guard at the shared `_guaranteed_delivery` preparation boundary as well as the direct tool path, and define precedence versus direction and key-validation errors. Test kill/leave racing send, name reuse, stale `deliver_pending`, missing-key follow-up, and valid-key follow-up.

7. **The shared-Claude-Desktop-process risk must be a release gate, not a documented limitation.**
   - **Problem:** The plan acknowledges that one Desktop MCP process may serve multiple conversations, but proposes shipping with a “one join per app process” note if that is true (`docs/features/external-agent-join/plan.md:386-392`). That does not contain the risk. Every conversation sharing the process would immediately observe the rebound globals and could read the joined child's inbox or send as it; the current tools derive authority solely from process-global `IDENTITY` and `_session_id` (`src/claude_teams/server_simple.py:160`, `345`, `2475-2481`, `2551-2553`). The “already leading” guard only checks prior registry activity and cannot distinguish simultaneous clean conversations.
   - **Suggested fix:** Make empirical process-model verification a pre-implementation/release gate. If Desktop starts one isolated MCP server per conversation, record repeatable evidence and test the process assumptions. If it shares one process, this process-global design must not ship; use a separately launched per-conversation bridge/server with identity in its environment, or a request/client-scoped identity mechanism. I cannot verify Desktop's actual process model from this repository, so the plan must not assume the favorable result.

8. **The status design does not satisfy the PRD and the “no branch needed” claim is false.**
   - **Problem:** The PRD explicitly requires the external backend label in `list_agents`, `agent_status`, and `check_agent` (`docs/features/external-agent-join/PRD.md:52-54`, `184-187`). `check_agent` and compact `list_agents` do include `backend` (`src/claude_teams/server_simple.py:1299-1318`, `4624-4655`), but `agent_status`'s exact row omits it (`src/claude_teams/server_simple.py:4709-4749`) and its docstring promises an exact schema without it (`src/claude_teams/server_simple.py:4752-4764`). Therefore the plan's statement that all three already surface the backend is factually wrong (`docs/features/external-agent-join/plan.md:326-330`).
   - **Honesty issue:** With no correlation field, the generic binding resolver labels an external record `legacy` (`src/claude_teams/agent_output.py:1176-1180`), even though it is not an old resumable backend record. Compact status with a marker avoids the scan, but `check_agent` and full list still expose this misleading binding result (`src/claude_teams/server_simple.py:2689-2708`, `4673-4704`).
   - **Suggested fix:** Add `backend` to `agent_status` (updating its exact schema, docstring, disk note, reference docs, and tests) or explicitly obtain a PRD disposition. Special-case external binding as `not_applicable`/`None` rather than `legacy`, while retaining marker/PID heartbeat behavior. Add direct tests of all three public tools and exact external rows.

9. **The acceptance matrix omits several safety-critical assertions and does not assert the existing ACs fully.**
   - **Problem:** The happy-path test checks a partial disk record but never calls the lead's `list_agents`, and omits exact assertions for `name`, `session_id`, `parent`, PID/token, returned paths/instructions, and one-row/no-duplicate invariants (`docs/features/external-agent-join/plan.md:356-365`). AC6's post-kill refusal is absent (`docs/features/external-agent-join/plan.md:372`; requirement at `docs/features/external-agent-join/PRD.md:267-269`). There is no `leave_team` test at all even though it is a new tool (`docs/features/external-agent-join/plan.md:321-325`, `348-350`). Heartbeat coverage tests only `read_messages`, not the promised `send_message` activity bump (`docs/features/external-agent-join/plan.md:375`; promise at `docs/features/external-agent-join/plan.md:208-217`). The restart test asserts a result that is false in the same-cwd candidate scenario described in blocker 3 (`docs/features/external-agent-join/plan.md:376`).
   - **Missing adversarial cases:** No test covers two processes joining the same token concurrently, two different join calls racing in one process, expired-ticket pruning/used retention, store write failure/crash reconciliation, spawn-after-ticket name reservation, raw `AGENT_SESSION_ID`, exact binding/auto-adopt eligibility, send racing leave/kill, send to a left child, stale `deliver_pending`, deregistered external tool calls, status-tool exact output, or parent disappearance before a mid-level ticket is consumed. The current code's cross-process registry lock (`src/claude_teams/server_simple.py:499-508`) and in-process-only inbox lock (`src/claude_teams/server_simple.py:440-457`) make these distinct concurrency classes.
   - **Suggested fix:** Expand §5 into explicit red tests for every case above. For concurrency tests, use barriers and separate processes where cross-process locking is the behavior under test. For restart safety, retain the real root binding and run same-cwd/auto-adopt-on. For kill, assert both `owns_process` and `kill_process` are never called for external records, then assert all later identity-bearing calls refuse.

## Non-blocking findings

1. **The kill correction is justified, but “would return True” is conditional rather than unconditional.**
   - **Evidence:** The record stores `creation_token(os.getpid())` in the proposed design. `owns_process` returns true for a live PID only if in-memory ownership exists or the live creation token matches the expected token (`src/claude_teams/backends/process_manager.py:300-347`). Thus it will normally prove ownership of the Desktop server when token capture succeeds, but a `None`/unreadable token fails closed. Current `kill_agent` kills whenever that boolean is true (`src/claude_teams/server_simple.py:4491-4496`). Backend `external` must therefore unconditionally skip destructive process operations, as the plan says (`docs/features/external-agent-join/plan.md:300-311`).
   - **Suggested fix:** Phrase the claim as “can/will under a successfully captured matching token,” and make the test assert that neither `owns_process` nor `kill_process` is called—not only that `kill_process` is not called.

2. **The `_annotate` characterization is overstated.**
   - **Evidence:** `_annotate` itself is at the cited location (`src/claude_teams/server_simple.py:831-838`), but not every dict-returning tool wraps it. `kill_agent`, `resume_session`, and `session_info` return raw `run_blocking` results (`src/claude_teams/server_simple.py:4512`, `4564`, `4611`), while spawn/send/read/check/follow-up do annotate. The plan says “every dict-returning tool wraps its result” (`docs/features/external-agent-join/plan.md:112-114`).
   - **Suggested fix:** State the actual subset and decide deliberately whether each new tool should surface recovery nudges. In particular, `join_team` should not leak a stale pre-join root recovery note; blocker 1 requires clearing it.

3. **Mid-level ticket parent liveness is unspecified.**
   - **Evidence:** The plan allows any resolved identity to issue and stores that identity as parent (`docs/features/external-agent-join/plan.md:150-156`, `405-409`). Parent routing relies on `_AGENT_PARENT_NAME`/`_spawner_target` rather than a tree (`src/claude_teams/server_simple.py:1021-1027`). If a mid-level parent is killed before ticket consumption, the join creates an orphaned child edge unless parent activity is revalidated.
   - **Suggested fix:** Either revoke/refuse open tickets whose non-root parent record is absent/inactive at consumption, or explicitly accept orphan joins and document recovery. Add a test.

4. **CLI watcher usability should be documented with the existing explicit reader option.**
   - **Evidence:** A fresh Desktop process's environment remains without `AGENT_NAME`, so the CLI defaults to `team-lead`; however, `watch` and `inbox-status` already support `--reader` (`src/claude_teams/cli.py:488-551`, `659-688`). Process-global MCP mutation does not mutate a separately launched CLI's environment.
   - **Suggested fix:** Have `join_team` return a paste-ready `watch_argv` using `--reader <external-name>` if this is advertised, rather than implying ambient identity will make the existing CLI watch the child automatically.

5. **The file-change/workflow list should include implementation evidence and targeted existing schema tests.**
   - **Evidence:** The plan lists production/tests/reference/README changes (`docs/features/external-agent-join/plan.md:343-354`) but the repository workflow requires `implementation.md` and a post-implementation review artifact (`CLAUDE.md`, “Feature documentation” and “Required feature workflow”). The `agent_status` exact schema and recovery behavior require edits to existing tests, not only a generic `tests/test_*` placeholder.
   - **Suggested fix:** Name the concrete existing test modules after discovery and include `docs/features/external-agent-join/implementation.md` plus implementation-review disposition in the work breakdown.

## Things the plan got right

- It correctly identifies that `RECIPIENT_CHILD` currently routes to `_guaranteed_send`, while the spawner path appends to an inbox (`src/claude_teams/server_simple.py:2446-2485`); an explicit pull-only external path is required.
- It correctly avoids registering `external` as a spawn backend. The generic follow-up path asks `registry.get(backend)` and requires resumability (`src/claude_teams/server_simple.py:3020-3037`), neither of which applies to Desktop.
- It correctly uses `spawned_by` for direction classification and writes both `parent` and `spawned_by` consistently with spawn records (`src/claude_teams/server_simple.py:2363-2391`, `1063-1073`).
- It correctly chooses the existing cross-process registry lock rather than an in-process-only lock for ticket/name coordination (`src/claude_teams/server_simple.py:499-508`, `440-457`). The missing piece is transaction semantics and making spawn honor reservations.
- It correctly keeps external delivery honest as `delivery: "inbox"` rather than claiming guaranteed receipt, and correctly requires `kill_agent` never to signal an external PID.
- It correctly rejects unresolved sentinel identities. `_require_resolved_identity` exists specifically to stop blank-name spawned workers from masquerading as root (`src/claude_teams/server_simple.py:738-760`), and Pi supplies the spawned signal plus literal per-agent MCP config (`src/claude_teams/backends/pi.py:374-444`).
- The rationale for not writing a naïve child-keyed or root-keyed positive binding is sound; only the stronger conclusion that no binding is sufficient for restart safety is wrong (`src/claude_teams/server_simple.py:462-472`, `585-630`).
