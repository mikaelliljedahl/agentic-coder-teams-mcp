# Independent plan review: codex-trust-prompt

**Verdict: REJECT as written.** The opt-in, per-process trust override is a sound direction, but the proposed marker-age test can label a healthy agent as blocked, and the Windows fallback has not established safe argv delivery. Revise the plan and re-review those points before implementation.

## Source verification

I compared the plan with this worktree and Codex `rust-v0.156.1` under the supplied `codex-src/codex-rs` tree. The TUI calls `check_directory_trust` before `App::run` (`tui/src/lib.rs:1747-1775,1950-1975`), so an injected `SessionStart` marker cannot resolve that screen. `--dangerously-bypass-approvals-and-sandbox` does not bypass it; I found no dedicated CLI trust-skip flag in the shared options. `codex exec` does not render the screen (`exec/src/lib.rs:962-970`). The dotted `-c projects."<path>".trust_level=...` key fails because `config/src/overrides.rs:22` splits every dot and keeps quotes in the key. A single `projects={ '<path>' = { trust_level = 'trusted' } }` value parses as TOML and recursively merges into existing project entries (`utils/cli/src/config_override.rs:95-102`, `config/src/merge.rs:94-145`). It is a `SessionFlags` layer, not a write to `config.toml`; persistence happens on an explicit TUI trust choice (`tui/src/onboarding/onboarding_screen.rs:687-735`). These findings support the basic override design, subject to managed-layer precedence below.

## Findings

1. **Blocker — `spawned_at` is too late to identify this launch's first marker.** `spawn_agent` records it only after `b.spawn(request)` returns (`server_simple.py:3475-3502`). On Windows, `b.spawn` waits for the tab PID and a settle interval (`backends/process_manager.py:1080-1217`), while the child may already have emitted `SessionStart`. Follow-up resets `spawned_at` even later, after delivery confirmation (`server_simple.py:4290-4343`). A valid marker can therefore have `ts < spawned_at` and be reported as a suspected trust block 45 seconds later. **Recommendation:** capture a separate launch-start timestamp before invoking spawn/resume, or tag hook markers with a launch generation; use that for freshness, leaving `spawned_at` semantics intact. Add red tests for markers written during spawn and during follow-up before record finalization, as well as a stale marker from the previous generation.

2. **Major — the 45-second condition does not identify a trust prompt.** An alive child with no new marker may be doing slow authentication, model/MCP startup, or real work with a failed or unavailable hook. Headless Codex never shows the trust screen, and Pi's state extension can be absent even when `WIN_AGENT_TEAMS_STATE_HOOKS` is on (`server_simple.py:2970-2990,3034-3044`). A changed server environment also cannot prove which hooks the existing process received. `check_agent` may have post-launch transcript activity despite no marker. **Recommendation:** persist whether state hooks were actually wired and whether the launch was interactive, check for credible activity since launch, and word the generic signal as “no state marker since launch.” Give a folder-trust hint only for an interactive Codex process whose trust is not known. Keep `state` and `stalled` unchanged. Test headless, missing Pi extension, post-launch transcript activity, slow but live startup, and a hooks-enabled-at-spawn versus disabled-at-read change.

3. **Major — the trust lookup and security scope are narrower in the plan than in Codex.** `ConfigToml::get_active_project` checks canonical/raw cwd then main-repo root (`config/src/config_toml.rs:850-918`), including linked worktrees (`git-utils/src/trust.rs:13-130`). But project-layer loading separately checks each directory, then a discovered **project root**, then the main-repo root (`config/src/loader/mod.rs:1035-1074,1245-1283,1640-1705`). The project root can come from configured markers other than `.git`. An exact-cwd override can clear the startup prompt while ancestor `.codex` layers remain disabled under an explicit ancestor `untrusted` entry; conversely, trusting a worktree directory can enable its local config and, for linked worktrees, hooks sourced from the main checkout (`loader/mod.rs:1760-1810`). Legacy managed file/MDM config has precedence above `SessionFlags` (`config/src/config_layer_source.rs:35-55`), so `trust_cwd=True` cannot promise to override a managed `untrusted` decision. **Recommendation:** distinguish the TUI's active-project lookup from per-layer project trust in §2.2 and the tool docstring. State that the flag requests trust for the cwd, may expose related project hooks, and may be overridden by managed policy; test explicit ancestor and managed-untrusted cases.

4. **Major — Windows argv safety is not demonstrated for every supported launch path.** The normal Windows Terminal path writes a PowerShell wrapper and quotes each argv element (`backends/process_manager.py:1110-1150,1240-1277`), and native `codex.exe` avoids `cmd.exe`. But `CodexBackend.discover_binary` deliberately falls back to `codex.cmd` (`backends/codex.py:284-335`), while direct Windows Terminal launch is opt-in and passes argv through `wt.exe` (`process_manager.py:1124-1147`). Existing hook code documents that `wt.exe` mangles embedded TOML double quotes (`hooks.py:368-385`). The proposed basic-string fallback for an apostrophe-containing path introduces exactly those quotes. `cmd.exe` also has special treatment for `%`, `!`, `&`, `^`, and other characters; a list of Python argv strings alone does not prove the shim round-trips the override. **Recommendation:** test the actual PowerShell-wrapper/native-exe, direct-`wt.exe`, fresh-console, and `.cmd` fallback transports with spaces, apostrophes, backslashes, semicolons, `%`, `!`, `&`, and `^`. Fail closed for `trust_cwd=True` on any unverified transport/path combination, or require a native exe. Use a TOML basic-string encoder for apostrophes and control characters, then verify the resulting token reaches Codex intact. A POSIX newline in a directory name is another case the current “fallback only for `'`” rule misses.

5. **Major — the security rationale understates what explicit trust enables.** Codex gates project `.codex/config.toml`, hooks, and exec policies by trust (`config/src/loader/mod.rs:1082-1100,1640-1810`), and project config can add MCP servers/providers. Hooks can run before the agent handles its prompt. `--dangerously-bypass-hook-trust` applies to this server's injected session hooks, while project-layer hooks remain subject to directory trust. This is a material new execution path even when `permission_mode='bypass'` already removes sandbox/approval checks. An explicit `untrusted` entry may also be overridden by the per-launch flag unless managed policy wins. **Recommendation:** keep opt-in default false, but describe the pre-prompt execution risk and explicit-untrusted override plainly in `spawn_agent` and the reference doc; do not call the delta “small.” Avoid claiming the flag enables only the exact directory's files.

6. **Minor — the advisory parser is likely to misreport effective trust.** Reading only `$CODEX_HOME/config.toml` ignores system, selected-profile, cloud, managed, and CLI layers; Codex's configured project-root markers and validated linked-worktree resolution are also more involved than `.git` plus `commondir` (`config/src/loader/mod.rs:338-399,1245-1283`; `git-utils/src/trust.rs:13-130`). A warning is useful only if it does not label an effectively trusted cwd “untrusted.” **Recommendation:** omit the advisory for this change, or use a conservative `trusted in user file / not established / unknown` result and explicitly avoid presenting it as Codex's effective decision. If retained, test conflicting profile/managed entries and worktree metadata validation. It must remain advisory.

7. **Minor — the public status call sites need a consistent shape.** `_compact_check_view` receives only an internal payload, which currently lacks `cwd`, `spawned_at`, launch mode, and hook wiring (`server_simple.py:1918-1942,1959-2005`); the plan does not say how it obtains them. `_empty_agent_check` is a separate payload constructor (`:1792-1812`), and `list_agents` has its own row path (`:6291-6382`) that will still show the original ambiguous state. **Recommendation:** pass the record or a small launch-metadata object into the shared diagnostic helper, add false/null fields to the empty check result, and either add the signal to `list_agents` or document why that status surface differs. Test `check_agent(full=True)`, unknown names, both list modes, and resumed records.

8. **Minor — the proposed tests do not yet prove the risky behavior red-first.** `tomllib.loads` proves TOML syntax, not Codex's override parser, config precedence, Windows argv transport, or lack of persistence. The smoke's hash of the real `~/.codex/config.toml` can be affected by another Codex process. **Recommendation:** first add failing unit tests for both builders and the launch-freshness race, record their red results, then implement. Add an isolated `CODEX_HOME` integration check against installed 0.157.1 with an existing `projects` entry, explicit `untrusted`, and a fresh cwd; verify effective trust, marker arrival, and byte-for-byte unchanged user config after spawn **and follow-up**. Run the native Windows transport cases above, then focused tests and the four repository gates required by `CLAUDE.md`.

9. **Nit — correct two research statements.** `plan.md` §2.5 says interactive and headless builds “both go through the trust screen,” contradicting §2.1 and the `exec` path. §2.4 lists `<cwd>/config.toml` as a project-local layer; the loader reads `<dir>/.codex/config.toml` (`config/src/loader/mod.rs:1669-1710`). **Recommendation:** correct both descriptions so the diagnosis and security text track the code.

## Answers to the plan's open questions

1. **Per-spawn only.** An operator-wide environment default makes trust implicit for every newly encountered checkout and weakens the deliberate opt-in boundary. Revisit only with a separate policy design and explicit auditability.
2. **Do not apply `trust_cwd` to Claude Code in this feature.** Its bypass/dialog behavior is unverified, and there is no demonstrated per-launch equivalent. Either reject `trust_cwd=True` for non-Codex backends with a clear error, or explicitly document it as Codex-only; silent acceptance is misleading. Keep the Claude smoke as research for a separate change.
3. **Keep the existing state enum.** A new `starting` state would break consumers and would still be a heuristic. Add diagnostic fields after fixing the freshness and false-positive issues above.
4. **Drop the advisory for the first implementation.** The corrected no-marker signal and explicit opt-in cover the actionable workflow; a partial config-file mirror adds drift and confusing false warnings. If pre-spawn guidance is later needed, use Codex's effective config machinery or a strictly conservative “unknown” advisory.

This review is source-based; I did not run a live Codex or Windows smoke test, and the plan already identifies the 0.156.1 versus installed 0.157.1 version gap.

### Findings

1. **Blocker — follow-up transport rejection can happen after the delivery lease is reserved or the old agent is stopped.** Rev 2 says `_build_resume_request` revalidates `trust_cwd` and an unsafe follow-up returns an error (§3.3, test 16). Today `_build_resume_request` runs *after* `reserve_lease` inside `_prepare` (`server_simple.py:4675-4703`), outside the `_do_follow_up` cleanup `try/finally`; an exception there can strand the lease. If validation is deferred to `backend.resume`, `_mark_attempt_sent` and old-PID shutdown have already happened (`:4773-4795`). **Recommendation:** preflight the effective resume mode, binary, path, and transport before reserving the lease or changing the old process. Return a structured refusal while preserving the pending delivery row and old PID; put any post-reservation failure under guaranteed lease cleanup. Add a red test that an unsafe follow-up leaves the old agent alive, no lease held, and a retryable delivery state.

2. **Major — stale markers make the five status surfaces disagree about post-launch activity.** Rev 2 defines the suppression input as a *bound rollout's* `last_activity_at`, but `_agent_status_row` and `_list_agents_row` resolve bindings only when the marker has **no timestamp** (`server_simple.py:6296-6315,6386-6410`). A previous-launch marker with a valid old `ts` skips their rollout check, so those surfaces can report `no_marker_since_launch=True` while `check_agent` and `list_agents(full=True)` see current rollout activity and report false. The proposed helper takes a bare `activity_ts`, which also loses the binding outcome needed to establish credibility. **Recommendation:** treat a marker older than `launch_started_at` as absent for the *diagnostic* binding fallback, use bounded binding where the cheap path requires it, and pass a `BindingResult` or already-validated `credible_activity_at` into the helper. Test the same live record with a stale `waiting` marker plus post-launch bound rollout activity across all five surfaces; preserve the existing public `state`/`stalled` values.

3. **Major — file mtime is not necessarily agent progress, and `legacy` is not a positive binding.** `BindingResult.output.last_activity_at` is the transcript file's `stat().st_mtime` (`agent_output.py:1120-1141`), not the timestamp of an assistant/tool event. A resumed Codex rollout can be touched after launch while the TUI is still waiting, which would suppress the folder-trust hint; this needs a smoke check rather than an assumption. `legacy` uses a read-only fallback without the correlation-token validation (`agent_output.py:1172-1232`), so it should not be called the agent's *credible* activity. **Recommendation:** prefer a post-launch event from a positively `bound` transcript (or use mtime only as an explicitly weaker heuristic), exclude `legacy` from the “credible” rule, and test an old bound rollout whose mtime advances without a marker. The diagnostic field name should reflect its full predicate: `no_marker_since_launch=False` currently also means “marker missing but transcript active,” which is not literally what the name says; use a suspicion name or separate the factual marker condition from the suppression condition.

4. **Major — the Windows override may not beat a user `untrusted` entry with different casing.** Codex lowercases the Windows *lookup* key, then checks `projects.get(lowercase_key)` before examining case-insensitive matches (`codex-rs/config/src/config_toml.rs:878-918`). If user config contains `projects.'c:\repo'.trust_level='untrusted'` and the injected key is `C:\Repo` from `Path.resolve()`, both distinct TOML keys survive the deep merge and the exact lowercase user key wins. Rev 2's assertion that `-c` overrides a user `untrusted` entry (§2.2, §3.5) is therefore conditional. **Recommendation:** use Codex's ASCII-lowercased canonical key on Windows, or otherwise guarantee the injected key wins the lookup; test mixed-case existing user entries, including an explicit `untrusted`, on Windows. Qualify the docstring until that is proven.

5. **Major — accepting `trust_cwd=True` headlessly is a successful no-op with a later trust change.** `codex exec` does not show the screen, but project config, hooks, and policies are still trust-gated (`codex-rs/config/src/loader/mod.rs:1035-1100,1640-1712`). A caller asking to trust the cwd gets an accepted spawn with `trust_cwd_applied:false` and different project behavior from the draft `spawn_agent` description. If the stored `trust_cwd=True` is reapplied on a later interactive follow-up, trust can become active on that follow-up without a new choice. §3.3 also says headless is accepted before transport checking, while §3.4 W5 says a `codex.cmd` shim is an error “on any transport.” **Recommendation:** choose one consistent contract: reject headless `trust_cwd=True` as inapplicable before creating a session, or apply the override headlessly too and document the project-code risk. Define follow-up mode changes explicitly and make W4/W5 precedence and tests agree. If keeping the no-op design, the tool docstring must say that no trust is granted on that launch and that a later interactive follow-up may apply it.

6. **Minor — two launch-metadata details need tightening.** `claude-code`'s `hooks_settings_path` can be present while `_hooks_settings_args()` returns `[]` under `WIN_AGENT_TEAMS_STATE_HOOKS=0` (`backends/claude_code.py:242-256`), so §3.1 would persist `hooks_wired=True` for a hookless launch. Also “same host clock” does not prevent `time.time()` stepping backward between the parent capture and the child hook write (`hooks.py:84-116`); equality with `launch_started_at` is not a durable generation proof. **Recommendation:** derive `hooks_wired` from the actual hook arguments at launch, including the Claude kill switch, and test it. Either tag markers with a launch identifier or document/test the bounded wall-clock limitation; do not claim clock changes are impossible.

7. **Nit — the TOML literal-string rule contradicts its own no-double-quote claim on POSIX.** A POSIX cwd may contain `"`; TOML permits it inside a single-quoted literal, but §3.4 rejects only `'`, C0 controls, and DEL while saying the token contains no `"`. **Recommendation:** scope the no-double-quote invariant to Windows paths, or reject `"` and test it. The literal-string approach otherwise preserves Windows backslashes and spaces correctly, subject to the required native Windows smoke.

The revised plan remains source-based. I did not run the installed Codex or Windows transport smoke, so the prescribed integration checks remain necessary before the PR leaves draft.

### Completion blockers (disposition during implementation)

1. **Major, Part B — the named lease-release helper cannot be called at the proposed catch point yet.** `_build_resume_request` runs after `reserve_lease` and before `_FollowUpPlan` is constructed (`server_simple.py:4661-4725`). `_release_lease_or_warn(session_id, plan)` requires `plan.agent_name` and `plan.operation_id` (`:4850-4875`); on an exception from `_build_resume_request`, `plan` does not exist. **Recommendation (disposition during implementation):** extract a release helper taking `(session_id, agent_name, operation_id)` and use it in both the new catch and the existing finalizer, retaining its retry/read-back behavior. Alternatively construct a lease handle before request building. The red test in §4.B7(6) must assert that the lease is actually gone after an injected request-build failure, including a failed first release attempt.

2. **Major, Part B — place the preflight after existing receipt reconciliation and keep the delivery response consistent.** The interval described in §4.B2 includes `_reconcile_pending_delivery` and `_answer_reconciled_attempt` (`server_simple.py:4560-4591`). Inserting immediately after `if not binding.bound` would return `trust_cwd_unsafe_transport` before reporting that an earlier attempt was already delivered. `_refuse` also returns a reason/retriable payload without the durable row's `status`, `phase`, and idempotency identity (`:4527-4542`), while `_guaranteed_send` has already opened that row (`:5567-5665`). **Recommendation (disposition during implementation):** insert the trust preflight after the reconciliation block and before `if alive`, then wrap its refusal with the pending delivery row's public status/identity without settling it. Test both an already-reconciled receipt and a new unsafe follow-up: the former still reports delivered; the latter remains queued/pending, has its idempotency key, holds no lease, and never stops the old PID.

3. **Major, Part A — calling `b.state_hook_args(request)` directly breaks non-BaseBackend adapters and the current type contract.** `registry.get()` returns the `Backend` protocol, which has no such method (`backends/contracts.py:264-335`), and the registry accepts third-party adapters (`backends/registry.py:87-94`). Several test fakes likewise do not inherit `BaseBackend`. A direct call would raise at spawn, even with `trust_cwd` absent, and can fail `ty check`. **Recommendation (disposition during implementation):** use an optional capability lookup that yields `[]` for adapters without it, or deliberately extend the protocol and update every registered/test adapter. The optional route preserves compatibility and records `hooks_wired=False` for an unknown backend. Add a spawn test with a minimal adapter lacking `state_hook_args`, plus the full type gate.

4. **Major, Part B — keep preflight and the launched command bound to the same effective transport.** The backend currently discovers its binary when `build_resume_command` runs inside `backend.resume` (`backends/process_base.py:90-93`; `backends/codex.py:404-420`), after the proposed preflight and after old-PID handling. A changed executable resolution or launch-mode flag could make the actual command differ from what preflight approved, so a late builder rejection can still occur after stopping the old agent. **Recommendation (disposition during implementation):** pin the resolved binary/mode for the attempt or verify the fully built command before shutting down the old PID; ensure the builder itself still refuses unsafe direct/shim paths. Add one test that changes the mocked resolution between preflight and resume and confirms the old agent remains alive.

### Test and documentation polish

5. **Minor, Part B — prove the Windows smoke uses the intended Codex home.** An existing Windows Terminal window does not inherit the launcher process's environment; its `.ps1` wrapper sets only `build_env(request)` entries (`backends/process_manager.py:1140-1162,1240-1277`). `CodexBackend.build_env` does not currently include `CODEX_HOME` (`backends/codex.py:627-652`). A smoke that sets isolated `CODEX_HOME` only on the server can silently exercise the real user config in W1. **Recommendation (disposition during implementation):** explicitly convey the isolated `CODEX_HOME` to the tab wrapper for this smoke (or use a fresh controlled terminal profile), verify the child reports that home, and compare its `config.toml` bytes before and after W1/W3 tests. Keep the PR draft until those tests pass.

6. **Minor, Part A — make the factual field's timing and liveness gates explicit.** `no_marker_since_launch=False` before 45 seconds, for a dead agent, or when hooks were not wired, even if there has literally been no marker; `None` means legacy/external. The headless hint's “crashed CLI” is also inconsistent with the required `alive=True` predicate (§3.A2). **Recommendation (disposition during implementation):** state the exact tri-state predicate in tool descriptions and the reference doc; say “CLI startup problem” or “hook failure” in the headless hint. Keep the field name if consumers are given this definition. Test the dead and threshold cases already listed in §3.A5.

Part A's `launch_started_at` capture points are correctly before child startup, including the follow-up capture after old-PID shutdown. Its raw-marker comparison is internally consistent and deliberately leaves the existing public `state`/`stalled` logic untouched. Part B's Windows argv and Codex trust behavior remain source-supported but unverified on installed 0.157.1; the plan correctly keeps that PR draft until the native Windows smoke passes.
