# Native session wake — pre-implementation smoke run (2026-09-25, Linux)

Goal: prove, before building anything, that both hosts can be woken natively
while idle — Claude Code through its session inbox socket, Codex through
`codex queue` — so a lead and a joined external member converse without a
human nudging either side.

Environment: Omarchy Linux, Claude Desktop running `claude` CLI 2.1.280
(`CLAUDE_CODE_ENTRYPOINT=claude-desktop`), codex-cli 0.156.1, Codex Desktop
(ChatGPT app) with its own `codex app-server` 0.155.0-alpha.

## 1. Claude session inbox socket

Documented at <https://code.claude.com/docs/en/cross-session-messaging.md>
("The session's inbox socket"). The session exports
`CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`; both were
also present in the environment of a lead's `claude_teams.server_simple`
process (a direct MCP child of the `claude` process). Wire format used, one
JSON object per line:

```text
{"type":"auth","token":"<CLAUDE_CODE_MESSAGING_TOKEN>"}
{"type":"user","message":{"role":"user","content":"<notice text>"}}
```

| # | Poster | Session state | Result |
|---|---|---|---|
| 1a | `setsid nohup` detached grandchild | idle | **Not delivered** (own-child ancestry lost; treated as a peer message) |
| 1b | direct child (Bash → python) | mid-turn | Delivered between tool calls |
| 1c | direct child, still alive, posting after 30 s | idle | **New turn started** with the notice |

Conclusion: the post must come from the MCP server process itself (or a
direct, non-detached child of it).

## 2. `codex queue` against a spawned Codex TUI agent

Spawned `codex-queue-probe` (backend `codex`, tier `cheapest`) in this repo,
waited for its first turn to end, then
`codex queue --thread <thread-id> --message "QUEUE-WAKE-TEST: ..."`.
The idle TUI started a new turn with the queued text within ~4 s.
(First attempt with cwd in `/tmp` stalled on Codex's folder-trust prompt —
not answered, because the answer persists to `config.toml`.)

## 3. End-to-end: Claude lead ↔ Codex Desktop external member

Setup: `create_join_ticket("codex-desktop-probe")` from the Claude session;
a prototype bridge (`proto_bridge.py`, a live child of the Claude session)
counted lines in `inbox-team-lead.jsonl` and, on growth, posted
`[proto-bridge] N new inbox line(s) ... - call read_messages` to the Claude
socket. The Codex Desktop thread joined, ran `echo $CODEX_THREAD_ID`, sent
`THREAD <id>` with `external_send`, and ended its turn. No watcher and no
polling on either side.

| Step | Time (UTC) | Observation |
|---|---|---|
| Codex → lead `THREAD 01a0d9a9-…` | 17:43:40 | proto-bridge woke the idle Claude session |
| Lead `send_message` PING-1 + `codex queue --thread 01a0d9a9-…` | 17:43:46 | queue row created |
| Desktop app-server drains queue | ≈17:43:51 | `queued_items` back to 0 |
| Codex `external_read` + `external_send "GOT: PING-1 …"` | 17:44:00 | proto-bridge woke the idle Claude session |
| PING-2, Codex thread **open but not the visible thread** | 17:44:42 | queue drained by 17:44:46 |
| Codex reply `GOT: PING-2 …` | 17:44:53 | Claude woken again |

Round trip ≈ 11–14 s, dominated by the app-server's ~10 s queue poll.

## Not yet covered

- Codex Desktop fully closed, or thread unloaded, when the queue row lands
  (expected per source: stays queued until the thread is next loaded).
- Queueing while the Codex thread has a turn in progress (expected: dispatched
  when the turn completes).
- Native Windows (named pipe, auth line mandatory) — not exercised.
